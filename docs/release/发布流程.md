## 0. 本仓发版形态（与典型 C++ 项目的差异）

先说清差异，免得把不适用的一步硬套进来：

| 维度 | 本仓（Python 组合仓） | 典型单仓 C++ 项目 |
|---|---|---|
| 产物 | **无二进制产物**——交付物就是源码 + 三仓并排 | 需打包二进制 / 上传附件 |
| 附件 | 通常**无**（有则 ≤100MB，附件名不带路径分隔符） | 常有 |
| 依赖 | 三仓**源码并排**或环境变量指路（cordis 无 PyPI 发行） | 链接期依赖 |
| 版本号 | **两套**：组合仓版本 + 契约版本（见 `版本策略.md`） | 一套 |
| 门禁 | 装配门禁 + 互不引用扫描 + 全量回归 | 编译 + 测试 + 制品比对 |
| 镜像 | Gitee「仓库镜像管理」→ GitHub，**最短间隔 5 分钟** | 同 |

> ⚠️ **本仓最需要记住的一句**：
> **tag 的存在本身是一个对外承诺**——它说「这个组合能跑起来」。
> 「能跑起来」曾卡在 `pyglet` 未被声明（见 `发布清单.md` §3），
> **该缺口已于 2026-11-04 修复并纳入基线门禁**（见本文顶部状态更新）。
> ⇒ 前置已解除，但打 tag 仍须 P0 门禁全绿 + 主理人放行。

## 1. 准备：先把要发的东西准备好

### 1.1 确认发版范围

```bash
git log --oneline --no-decorate <上一个 tag>..HEAD
git status --short
```

> 本仓**首次发布**，没有「上一个 tag」⇒ 上界就是全部历史。
> 首次发布前**再确认一次版本号**：`pyproject.toml` 的 `version` 与要打的 tag 一致。
> 判定规则见 [`版本策略.md`](版本策略.md)。

### 1.2 更新 `CHANGELOG.md`

- 本次发版的内容写进 `## [x.y.z]` 段（**用户视角的变化**，不是 commit 标题搬运）。
- 尚未发布的内容留在 `## [Unreleased]` 段。
- 首次发布时，`## [Unreleased]` 空、`## [0.1.0]` 承载全部内容。

### 1.3 确认许可材料齐备

```bash
test -f NOTICE && echo NOTICE_OK
grep -q "Wizards of the Coast LLC" NOTICE && echo ATTRIB_OK
```

详见 [`发布清单.md`](发布清单.md) §1。**组合分发的义务不是「仓库里有 NOTICE」就完事了**——
发行版说明里也要有显著的 SRD 5.1 署名段。

## 2. P1 · 发版核心动作

> **顺序执行，幂等可重入**：每个子命令重复跑安全（已存在就 SKIP）；中断后直接重跑。

### 2.0 验令牌（最便宜的失败前置）

```bash
# 本机无文件式凭据（~/.git-credentials 不存在，凭据在 Windows 凭据管理器里）
# ⇒ 脚本取令牌必须显式给：
python <发版脚本> --token "<HEX>" whoami
#   或
export GITEE_TOKEN=<HEX>
```

> ⚠️ **两条独立链路，别互相推断**：`git push` 能推（GCM 自动取用），
> **不代表**发版脚本能取到令牌（脚本只认 `--token` / `--token-file` / `GITEE_TOKEN`）。
>
> ⚠️ **令牌红线**：令牌**绝不进仓库、绝不进提交、绝不回显**。
> 全文用 `<GITEE_TOKEN>` / `****` 表示。需要脱敏时：
> `... 2>&1 | sed -E "s/${TOKEN}/<REDACTED>/g"`

### 2.1 跑 P0 门禁（**在匿名 clone 副本上跑**）

```bash
# 本地跑通不算数 —— 本地有 .venv、有并排三仓、有 .gitignore 完整上下文
# 匿名副本才是「用户拿到手」的形态
git clone --depth 1 https://gitee.com/siwpan/superengine.git /tmp/verify
cd /tmp/verify && python -m tests.run_tests && python selfcheck.py
```

同时对照 [`发布清单.md`](发布清单.md) §P0 逐项勾完。

> **为什么要匿名副本**：本地工作区有 `.venv/`（已被 `.gitignore` 忽略），
> 你在本地跑的测试可能用的是 venv 里手工装的东西——而用户按 `requirements.txt` 装不到。
> **本轮实测的 `pyglet` 缺口就是这样被挡住的**：本地 venv 有 pyglet，
> 按文档装却没有。

### 2.2 推前：核对两端远端，确认无分叉

```bash
git fetch --all
git ls-remote origin
git ls-remote github
git status --short          # 必须为空
```

> **2026-10-29 实测踩过 `fetch first`**：远端可能已被他人 / 他机推进，
> 闷头一推就被拒。**先 fetch + ls-remote 看两端是否领先本地。**
>
> **本仓有两个远端，缺一不可**：
> `origin` = gitee `siwpan/superengine`（主）、
> `github` = github `siwpan95/superengine`（mirror）。
> ⚠️ **用户名不一致**是真实坑。

### 2.3 推代码

```bash
# 优先推主远端（gitee）
GIT_TERMINAL_PROMPT=0 git push origin master
# 再推镜像远端（若直连可用）；不可用时走 Gitee 镜像，见 §2.6
GIT_TERMINAL_PROMPT=0 git push github master
```

> **`GIT_TERMINAL_PROMPT=0` + `GCM_INTERACTIVE=never`**：从两层封死「等待输入」。
> 前台推送会把一个回合吃满 120s 并被工具超时杀掉；**同一条命令放后台即刻成功**
> ——所以长耗时的推送放后台执行。
>
> 写权限确认**不要用 `--dry-run`**：本地已最新时它输出 `Everything up-to-date`，
> **根本没走鉴权**，会误判。用**分支探针**：
> `git branch -f __probe master` → push 该分支 → `push --delete __probe`
> → `git ls-remote --heads` 确认远端只剩 master。

### 2.4 推后：复核 IN_SYNC（**不轻信 push 的输出**）

```bash
git rev-parse HEAD
git ls-remote origin refs/heads/master
```

两串必须**逐字符相等**。`git push` 的回执是「推送动作」的回执，
**不是「远端确实同步」的证据**——同步状态**只信 `git ls-remote`**。

### 2.5 打 tag

```bash
git tag -a v0.1.0 -m "v0.1.0"
git push origin v0.1.0
```

> **tag 必须先于 release**——平台不允许跳过 Tag 直接建 release。
> tag 指向的 commit **必须就是全量回归通过的那个**，
> 不是「后来又改过」的那个。
>
> **本仓首次发布的前置**：确认 `pyglet` 依赖声明已补全（§0 末尾）。

### 2.6 GitHub 镜像同步（**最短间隔 5 分钟**）

```bash
git ls-remote --tags github
```

> **本机到 GitHub 的直连不可依赖**（3dworld 的 CI 已实证 `curl api.github.com` /
> `github.com` 都拿不到响应）。本仓靠 Gitee 的「仓库镜像管理」从**服务器侧**推到 GitHub，
> **最短间隔 5 分钟**。
>
> ⇒ **推完 tag 后 GitHub 侧不会立刻可见。别把「GitHub 上还没看到 tag」当成推失败。**
> 等镜像跑完再复核；复核前**不要**基于 GitHub 侧的状态做任何判断。

### 2.7 建 release

```bash
python <发版脚本> --token "<HEX>" \
       release --tag v0.1.0 --title "v0.1.0" --notes-file RELEASE_NOTES.md
```

发行说明**从 `CHANGELOG.md` 的 `0.1.0` 条目取**，并补齐这几段：

- 系统要求（Python ≥3.11、四仓并排、cordis 来源）
- 安装步骤（按 `docs/新人开发上手指南.md` 第二节）
- **许可与对应源码**（MIT + SRD 5.1 / CC-BY-4.0 署名 + `git clone` 源码地址）
- 本版本实测数据（回归 6/6、selfcheck 23 项、boot OK）
- **已知限制（如实列）**——见 `CHANGELOG.md` 的「已知限制」段

> **平台坑**：响应里的 `html_url` 可能是 `null`，拿不到发行版网页地址时
> 自己拼 `https://gitee.com/{owner}/{repo}/releases/{tag}`。
> `GET /releases/tags/{tag}` 对不存在的 tag 返回 **200 + `null`**（不是 404）——
> 判据要用 `isinstance(d, dict) and d.get("id")`，别只判状态码。

## 3. P2 · 收尾与验收

> **别停在「上传成功」。**

### 3.1 三层硬证据（前两层足够下结论）

```bash
# ① 远端 ref 与本地 HEAD 逐字符相等
git rev-parse HEAD
git ls-remote origin refs/heads/master

# ② 关键文件字节级在远端
git rev-parse HEAD:NOTICE
git cat-file -s <上面那个 sha>      # ⚠ 用 blob 口径，别用文件大小
# 匿名比对：
curl -s "https://gitee.com/api/v5/repos/siwpan/superengine/contents/NOTICE?ref=master"
#   → .sha 与上面一致、.size 与 blob 大小一致

# ③ 工作区干净
git status --short
```

> **先比 blob sha，sha 相同就是同一份内容**——有 `.gitattributes` 时
> 工作区 CRLF / 仓内 LF，文件大小每行差 1 字节（实测 20277 vs 19950）。
> 中文路径过滤一律加 `-c core.quotepath=false`。

### 3.2 匿名视角复验

- 不带令牌能打开仓库页 / raw / 发行版页
- **匿名 clone 能拉全**：文件数 + commit 号与本地一致
  （比「网页能开」强得多，且验证无私有依赖）

### 3.3 卫生复查

- [ ] `.git/config` 无凭据残留
- [ ] 远端只剩 `master`（探针分支已删）
- [ ] 发行版指向的 commit 即绿状态那个
- [ ] `CHANGELOG.md` 已更新（本次内容在版本段，后续在 `Unreleased`）
- [ ] `NOTICE` 随分发物携带，署名段完整

### 3.4 若发版出问题：回滚

| 情形 | 处置 |
|---|---|
| release 建错（草稿） | 可删；**已发布**的 release 在网页端不可直接删（需先取消「最新发布」再联系管理员）——但 API 实测 `DELETE /releases/{id}` → 204 仍可删（附件随之清空） |
| 附件传错 | `assets` **没有 `id` 字段**（API 只回 `name` + `browser_download_url`）⇒ 传错删不掉。**正确做法：删整个 release 再重建**（`DELETE` → 204 → 重新 `release` + `attach`） |
| tag 打错 | ⚠️ **tag 一旦推上去就是公开历史**。删 tag 需要重写远端 ref（`git push --delete origin v0.1.0`），
  但**已被人 clone 过的 tag 删不回来**。⇒ 打 tag 前**逐字核对版本号**。 |
| 代码发错（commit 内容有问题） | **不要 force push**。走新 commit 修复 → 重新发版。
  公开仓的历史是永久的，改不回来。 |

## 4. 幂等与可重入（工作区通用纪律，逐条保留）

| 纪律 | 在本仓怎么落地 |
|---|---|
| **幂等** | 每个发版子命令重复跑安全（已存在就 SKIP）；中断后直接重跑，不从头来 |
| **可重入** | 失败后**修那一处**再重跑该步，不要重跑整条链 |
| **令牌脱敏** | 令牌绝不进仓库、不进提交、不回显；输出过令牌时用 `sed` 脱敏 |
| **不轻信输出** | 同步状态只信 `git ls-remote`；写权限只信分支探针；不拿 `--dry-run` 当鉴权依据 |
| **门禁在匿名副本上跑** | 本地跑通不算数（本地有 `.venv` 与并排三仓） |
| **长耗时操作放后台** | 前台推送会被 120s 工具超时杀掉；后台即刻成功 |

## 5. 本机落点（换机后先复核，别照抄）

> **通用纪律**：绝对路径都属于**某台机器**，不是事实。换机后先跑下面这段只读命令复核，
> 再照抄上面的命令。

```bash
git config --global --get user.name        # 本机：全局已配 siwpan
git config --global --get user.email
ls ~/.git-credentials 2>/dev/null || echo "无文件式凭据（凭据在 GCM）"
git ls-remote origin "refs/heads/$(git rev-parse --abbrev-ref HEAD)"
```

| 项 | 本机现状（2026-11-04 实测） |
|---|---|
| git 身份 | **全局**已配 `siwpan <siwpan@users.noreply.gitee.com>`（本仓无仓库级覆盖） |
| 凭据 | Windows 凭据管理器（GCM）持有；**无** `~/.git-credentials` |
| `git push` | 由 GCM 自动取用，实测不弹窗、可推 |
| 发版脚本取令牌 | **必须显式给** `--token` / `--token-file` / `GITEE_TOKEN` |
| 双远端 | gitee `siwpan`（主）/ github `siwpan95`（mirror） |
| 本机→GitHub 直连 | 依赖 Gitee 镜像（服务器侧，**最短间隔 5 分钟**） |
| 路径约定 | **去符盘**——文档里举绝对路径用 `/repos/superengine`，不写盘符 |

## 6. 一键速查（令牌脱敏）

```bash
# —— 0. 准备 ——
git fetch --all && git ls-remote origin && git ls-remote github
git status --short                                   # 必须为空

# —— 1. 门禁（匿名副本上跑）——
git clone --depth 1 https://gitee.com/siwpan/superengine.git /tmp/verify
cd /tmp/verify && python -m tests.run_tests && python selfcheck.py && cd -

# —— 2. 推代码 ——
GIT_TERMINAL_PROMPT=0 git push origin master
GIT_TERMINAL_PROMPT=0 git push github master         # 直连不可用时走 Gitee 镜像

# —— 3. 推后复核（不轻信 push 输出）——
git rev-parse HEAD
git ls-remote origin refs/heads/master               # 两串须逐字符相等

# —— 4. 打 tag（前置已解除；仍须 P0 全绿 + 主理人放行）——
git tag -a v0.1.0 -m "v0.1.0" && git push origin v0.1.0

# —— 5. GitHub 镜像复核（最短间隔 5 分钟，等镜像跑完再看）——
git ls-remote --tags github

# —— 6. 建 release ——
python <发版脚本> --token "<HEX>" release --tag v0.1.0 --title "v0.1.0" --notes-file RELEASE_NOTES.md

# —— 7. 三层验收 ——
git rev-parse HEAD && git ls-remote origin refs/heads/master
git rev-parse HEAD:NOTICE && git cat-file -s <sha>
git status --short
```
