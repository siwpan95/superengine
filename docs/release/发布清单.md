# 发布清单 —— 打 tag 前逐项过

> **用法**：这是**可勾选**的门禁清单，不是说明文。
> 每一项都写了**判据**（什么算过）和**怎么验**（跑哪条命令）。
> **任何一项没过，就不发版** —— 除非主理人明确豁免并留下豁免记录。
>
> **纪律**：本清单的门禁要能**在匿名 clone 副本上**跑通。
> 本地跑通不算数——本地有 `.gitignore` 的完整上下文、有 `.venv`、
> 有并排的三仓，这些都是 clone 的人不一定有的条件。
>
> 工作区规范（**不在本仓内**）：发版指南（`SPEC-102`）、推送流程（`SPEC-101`）、
> 铁律（`SPEC-001`）、路径与编码约定（`SPEC-006`）。
>
> **状态更新（2026-11-04，工程基线 / 质量门落地后）**：本清单初稿记录的
> `pyglet` 依赖缺口**已修复** —— `pyproject.toml` 声明 `pyglet==2.1.16`，
> `requirements.txt` 改为 `-e .` 转发到单一事实来源，并由
> `tests/test_baseline.py` 机械守卫；新增 `scripts/bootstrap.py` 一键引导与
> `.github/workflows/ci.yml` 三平台 CI；全量回归由 `6/6` 变为 **`7/7`**。
> ⇒ 由此解除「依赖补全前不打 `v0.1.0` tag」这一前置（§P1 第 1 步已同步）；
> 但打 tag 仍需**本清单 P0 全项通过 + 主理人放行**。下文保留的踩坑记录
> 仅作排障知识，不代表当前状态。

## P0 · 发版前门禁（机器拦，不可跳过）

### 1. 许可核查

- [ ] **根 `NOTICE` 存在**
      ```bash
      test -f NOTICE && echo NOTICE_OK
      ```
- [ ] **`NOTICE` 内容含 SRD 5.1 署名**（自检项：署名必须**逐字**完整，不是「有个链接就行」）
      ```bash
      grep -q "System Reference Document 5.1" NOTICE \
        && grep -q "Wizards of the Coast LLC" NOTICE \
        && grep -q "creativecommons.org/licenses/by/4.0/legalcode" NOTICE \
        && grep -q "dnd.wizards.com/resources/systems-reference-document" NOTICE \
        && echo NOTICE_ATTRIBUTION_OK
      ```
      > 四项都要命中。SRD 5.1 的署名要求是「标明来源 + 给出许可链接」，
      > 少任何一项都不构成合规署名。
- [ ] **GURPS 免责声明在位**（沿用 an-engine 的口径，本仓通过 `rules_kernel` 间接涉及其数据）
      ```bash
      grep -q "Steve Jackson Games" NOTICE && echo GURPS_DISCLAIMER_OK
      ```
- [ ] **根 `LICENSE` 存在且是 MIT**
      ```bash
      head -3 LICENSE | grep -q "MIT License" && echo LICENSE_OK
      ```
- [ ] **分发物随包携带 `NOTICE`**（组合分发的义务；不是把 `NOTICE` 放在仓库里就算完）
      - [ ] 发行版说明 / 附件里包含 `NOTICE`（或明确指向本仓的 `NOTICE` 路径）
      - [ ] 发行说明**显著位置**有 SRD 5.1 署名段（不是埋在附件里）
      - [ ] 若分发物含 an-engine 的代码或数据 → 一并携带 an-engine 的 `NOTICE`
- [ ] **无凭据残留**
      ```bash
      # 只报「有没有」，不打印值——url.*.insteadof 里可能内嵌令牌，打出来就等于回显
      git config --get-regexp 'credential|url\..*insteadof' >/dev/null && echo "见下方人工核对（勿整段回显）"
      git remote -v | grep -qE 'https://[^/@]+:[^/@]+@' && echo "FAIL: remote URL 内嵌凭据" || echo "OK: remote URL 无内嵌凭据"
      ```
      > 本机凭据由 Windows 凭据管理器（GCM）持有，`~/.git-credentials` 不存在——
      > 这意味着**取令牌的脚本必须显式给令牌**，`git push` 能推不代表脚本能取到令牌（两条独立链路）。
      > 核对 `credential.*` 各项时**只确认「指向哪里」，不要把值贴进日志 / 提交 / 发行说明**。

### 2. 全量回归绿

> **判据**：全部模块通过，**不是「看起来能跑」**。

- [ ] **全量测试**
      ```bash
      python -m tests.run_tests
      ```
      期望末行 `ALL_TESTS_PASSED`，且模块行 `7/7 通过`。
      > 模块数以 `tests/run_tests.py` 的 `MODULES` 表为准（当前 7 个：
      > 装配门禁 / 三仓互不引用 / 三仓流水线 / M3 热重载 / M4 多实现 / 开发循环 /
      > **回归基线 `test_baseline`**）。
      > 若质量面新增了门禁模块，以代码里的实际条数为准，**不要照抄本文档里的数字**。
- [ ] **无头自检**
      ```bash
      python selfcheck.py
      ```
      期望 `selfcheck ok: superengine contract layer (...)`。
      > 这一项**不导入 cordis、不导入三仓**——所以它能在 CI 里当第一道快速判据，
      > 失败时基本可断定是契约层本身坏了，而不是环境问题。
- [ ] **装配验证（headless）**
      ```bash
      python -m superengine.cli.boot --report
      ```
      期望末行 **`SUPERENGINE_BOOT_OK`**（失败则是 `SUPERENGINE_BOOT_FAILED`）。
      > 注意 `boot` 需要 cordis + watchdog + 三仓全部可导入；
      > 在某些环境 cordis 的 Hmr 导入会因 watchdog 失败——**此时用 `selfcheck.py` 兜底**，
      > 但 `boot` 不通仍然是发布阻断项（它验证的是三仓真能装上）。
- [ ] **测试是在**装了完整依赖的**解释器下跑的**
      ```bash
      python scripts/bootstrap.py --check-only     # 依赖 / 四仓 / cordis 就位
      ```
      > ⚠️ **历史事故（已修复，保留作排障知识）**：用没装 `pyglet` 的解释器跑，
      > 当时 6 个模块只有 1 个通过，失败信息长这样：
      > `RepoNotFound: 仓 '3dworld' 缺少 bridge 接口模块（world3d.bridge）…… 原始错误：No module named 'pyglet'`
      > ——**这个报错会把你引向错误的方向**（看起来像「三仓没就位」），
      > 实际根因是依赖缺失。现由 `test_baseline.py::test_pyglet_is_declared` 与
      > `bootstrap.py` 双重守卫；遇到 `RepoNotFound` 一律先读 `原始错误` 那一段。

### 3. 依赖声明完整性

> **判据**：`requirements.txt` 装完就能跑。**这是本轮实测踩到的真实坑。**

- [ ] **`requirements.txt` 装完，`import` 链一路通**
      ```bash
      python -m pip install -r requirements.txt
      python -c "import world3d.bridge; print('BRIDGE_IMPORT_OK')"
      ```
      > 装配路径会经 `world3d.bridge` → `world3d.engine.mathkit` → **pyglet**。
      > pyglet 是 **3dworld 侧**的依赖，但**本仓的装配路径会 import 到它**——
      > 所以本仓的 `requirements.txt` 必须能把它带进来，否则干净机必炸。
- [ ] **`pyproject.toml` 的 `dependencies` 与 `requirements.txt` 一致**
      > 两者现在都缺 `pyglet`。依赖声明的修法由工程面定（可能选择加 `pyglet`，
      > 也可能在 `requirements.txt` 里显式注明「pyglet 来自 3dworld 侧」并给出安装指引）——
      > 但**无论哪种修法，判据是上面那两条命令能过**。
- [ ] **本仓的 `requirements.txt` 与三仓各自的 `requirements.txt` 不冲突**
      > 尤其 pyglet：3dworld 另有 `requirements-pyglet1x.txt`（pyglet 1.5.30 锁版，cocos2d 兼容路线）。
      > 本仓走默认路线（pyglet 2.x），**不要把 1.x 那份拉进来**。

### 5. tag 与远端核对（两端！）

> **本仓有两个远端，缺一不可**：
>
> | 远端 | 地址 | 角色 |
> |---|---|---|
> | `origin` | `https://gitee.com/siwpan/superengine.git` | **主**（发版以此为准） |
> | `github` | `git@github.com:siwpan95/superengine.git` | **mirror**（由 Gitee「仓库镜像管理」从服务器侧推送） |
>
> ⚠️ **用户名不一致是真实坑**：gitee 上叫 `siwpan`，github 上叫 `siwpan95`。
> ⚠️ **本机到 GitHub 的直连不可依赖**（3dworld CI 已实证），
> 本仓靠 Gitee 镜像从**服务器侧**推到 GitHub，**最短间隔 5 分钟**。

- [ ] **推前：核对两端远端，确认无分叉**
      ```bash
      git fetch --all
      git ls-remote origin
      git ls-remote github
      ```
      > **2026-10-29 实测踩过 `fetch first`**：远端可能已被他人 / 他机推进，
      > 闷头一推就被拒。**先 fetch + ls-remote 看两端是否领先本地。**
- [ ] **推前：本地工作区干净**
      ```bash
      git status --short      # 必须为空
      ```
- [ ] **推后：同样用 `ls-remote` 复核 IN_SYNC**
      ```bash
      git rev-parse HEAD
      git ls-remote origin refs/heads/master
      ```
      两串必须**逐字符相等**。
      > **不轻信 `git push` 打印的输出** —— 那是「推送动作」的回执，
      > 不是「远端确实同步」的证据。同步状态**只信 `git ls-remote`**。
- [ ] **推后：tag 在**两端**远端都可见**
      ```bash
      git ls-remote --tags origin
      git ls-remote --tags github
      ```
      > GitHub 侧经 Gitee 镜像同步，**最短间隔 5 分钟**——
      > 推完 tag 后 GitHub 侧不会立刻可见。**别把「GitHub 上还没看到 tag」当成推失败**，
      > 等镜像跑完再复核。
- [ ] **确认远端确实没有分叉**（不是只看本地）
      > `ls-remote` 只给 ref 指向的 sha，**不给分叉历史**。
      > 若两端 sha 不等，先 `git fetch` 后对比 `git log --oneline --left-right origin/master...master`，
      > 确认是「本地领先」而非「两边各有提交」。

### 6. 中文路径 git 过滤必须带 `-c core.quotepath=false`

> **已犯三次的坑**（工作区铁律 3）：git 默认把非 ASCII 文件名转义成
> `"\347\233\256\345\275\225…"`，于是**按名字过滤恒假**，
> 会误判「这个文件不在仓库里」——2026-09-28 那次差点因此放弃恢复一个本来能恢复的文件。

- [ ] **核对发布物清单时，所有按中文名过滤的 git 命令都带了这个参数**
      ```bash
      git -c core.quotepath=false ls-tree -r --name-only HEAD
      git -c core.quotepath=false status --short
      git -c core.quotepath=false diff --name-only --diff-filter=D
      ```
      > 本仓的 `docs/新人开发上手指南.md` 正是中文文件名，
      > 每次核对「发布物里有没有该文件」都会撞上这条。

### 7. 编码卫生

- [ ] **所有 `.md` / `.txt` 为 UTF-8 无 BOM**
      ```bash
      head -c 3 CHANGELOG.md | od -An -tx1     # 不得出现 239 187 191
      head -c 3 NOTICE     | od -An -tx1
      head -c 3 docs/release/版本策略.md | od -An -tx1
      ```
      > 中文 Windows 下 Python 文本 I/O 默认 GBK，**往返改写会烤坏中文**。
      > 编辑工具可能**静默剥掉 BOM**——所以要**复核首三字节**，而不是相信编辑器。
- [ ] **提交信息里的路径不带反斜杠**
      > 提交信息**落文件再 `-F`**（`git commit -F /tmp/msg.txt`）：
      > 既避开编辑器弹窗，也避开 Windows 路径被 bash 吃掉反斜杠。

## P1 · 发版核心动作（顺序执行，幂等可重入）

> 每个子命令重复跑安全（已存在就 SKIP）。中断后直接重跑。

- [ ] **0. 验令牌**（最便宜的失败前置）
      > 本机无文件式凭据（`~/.git-credentials` 不存在，凭据在 GCM 里），
      > 所以脚本取令牌**必须显式给**：`--token "<HEX>"` 或 `export GITEE_TOKEN=<HEX>`。
      > **`git push` 能推 ≠ 脚本能取到令牌**，二者是两条独立链路。
- [ ] **1. 打 tag**（语义化版本，本仓首次发布即 `v0.1.0`）
      ```bash
      git tag -a v0.1.0 -m "v0.1.0"
      git push origin v0.1.0
      ```
      > **tag 必须在 release 之前**——平台不允许跳过 Tag 直接建 release。
      > ⚠️ **先确认 `v0.1.0` 这个号该由谁来定**：
      > 见 `docs/release/版本策略.md` §5——`0.1.0` 的前提是「本仓能独立跑起来」，
      > 而 `pyglet` 依赖声明补全落地之前这个前提**尚未兑现**。
      > **依赖没补全 ⇒ 不打这个 tag。**
- [ ] **2. 建 release**（发行说明从 `CHANGELOG.md` 的 `0.1.0` 条目取）
- [ ] **3.（如需）传附件** —— 本仓是纯 Python 源码仓，**通常无二进制附件**；
      若要传，单附件 ≤100MB、每仓总附件 ≤1GB，附件名**不带路径分隔符**（会丢目录结构）。
- [ ] **4.（如需）转公开** —— 本仓已是公开仓（铁律 0），一般无需此步。
      > 若需转：`PATCH /repos/{owner}/{repo}` 的 body **必须带 `name`**，否则 400。

## P2 · 收尾与验收

> 别停在「上传成功」。

- [ ] **三层硬证据**（前两层足够下结论）
  - [ ] ① 远端 ref 与本地 HEAD **逐字符相等**
        ```bash
        git rev-parse HEAD
        git ls-remote origin refs/heads/master
        ```
  - [ ] ② 关键文件**字节级**在远端
        ```bash
        git rev-parse HEAD:NOTICE
        git cat-file -s <上面那个 sha>     # ⚠ 用 blob 口径，别用文件大小
        ```
        再用匿名 contents API 比对 `.sha` 与 `.size`。
        > **先比 blob sha，sha 相同就是同一份内容**——有 `.gitattributes` 时
        > 工作区 CRLF / 仓内 LF，文件大小每行差 1 字节。
  - [ ] ③ 工作区 `git status --short` 为空
- [ ] **发行说明含**：系统要求 → 安装步骤 → **许可与对应源码** → 本版本实测数据 → **已知限制（如实列）**
      > 本仓「已知限制」见 `CHANGELOG.md` 的 `0.1.0` 条目那一节——
      > **如实列出来**，别只报喜。
      > 源码指向要写 `git clone` 地址：平台自动附的源码包链接**不是直链**
      > （匿名拿到的是 HTML 页面）。
- [ ] **匿名视角复验**：不带令牌能打开仓库页 / raw / 发行版页
- [ ] **发行版指向的 commit 就是全量回归通过的那个**（不是「后来又改过」的那个）
- [ ] **`.git/config` 无凭据残留**
- [ ] **CHANGELOG 已更新**：本次发版的内容已写进 `CHANGELOG.md`，
      未发布内容在 `## [Unreleased]` 段
      > 本仓**首次发布**，所以现在 `## [Unreleased]` 是空的、`## [0.1.0]` 承载全部内容。
      > 打完 tag 后，后续变更一律进 `Unreleased`。
