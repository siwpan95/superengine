## 0. 为什么必须是两套

三仓各自独立发版，节奏天然不同频（实测现状见 §4）。若契约版本跟随某一仓，
另外两仓就被那一仓的节奏绑架；若组合仓版本跟随某一仓，用户会误以为
「superengine v0.2.0 = 某个三仓升级了」，从而把**兄弟仓的发布节奏传导进组合仓**——
组合仓就会退化成三仓版本的影子，而它自己的装配层变化反而无处记录。

更根本的问题：**组合仓的版本号回答不了「我这次改了什么」这个问题**。
用户拿到 `superengine v0.2.0`，想知道的是：
契约接缝有没有变（会影响到我的提供方要不要改）？装配层有没有变（会影响到我的配置要不要改）？
这两件事的**影响面完全不同**，所以必须分开计量。

## 1. 两套计数器的定义

| | 组合仓版本号 | 契约版本号 |
|---|---|---|
| **载体** | `pyproject.toml` 的 `version` + git tag | `superengine/contracts/__init__.py` 的 `CONTRACT_VERSIONS` |
| **计量对象** | 装配 / 桥接 / 门禁 / 开发循环这一层 | 单个**跨仓接缝**的形状（方法签名与语义） |
| **粒度** | 全仓一个号 | **每个契约一个号**（当前 8 个，全为 `1.0.0`） |
| **谁可以改** | 本仓维护者（组合仓这一层归本仓） | 本仓维护者，且**必须**独立于任何一仓的发版 |
| **与三仓发版的关系** | **无**。兄弟仓发版不动它 | **无**。兄弟仓发版不动它 |
| **对使用者的影响** | 装配层行为变了（配置 / 命令 / 门禁可能受影响） | 接缝形状变了（提供方可能要改实现） |

**两套号互不派生**：`superengine v0.2.0` **不表示**任何契约是 `2.0.0`；
`CONTRACT_VERSIONS` 里全是 `1.0.0` 时，组合仓完全可能是 `v0.9.0`。
反过来也一样。

## 2. 组合仓版本号：什么时候该动，什么时候不该动

### 2.1 该动（bump）的判定规则

按**语义化版本**，但判据要落到「使用者会不会被打到」这一层：

| 级别 | 判据 | 典型例子 | 对使用者意味着 |
|---|---|---|---|
| **major** | 装配层的**对外契约**破了：现存的配置 / 命令 / 桥接入口写法不再成立 | 删掉或重命名一个 bridge 的 `provide` 名；`configs/cordis.super.yml` 的结构改到旧配置不再被接受；`python -m superengine.cli.boot` 的参数语义变化 | 升级要改配置 |
| **minor** | 装配层**向后兼容地**扩了：新增能力、新增门禁、新增可选契约，既有配置与写法继续成立 | 新增一个契约并加进 `CONTRACT_VERSIONS`；新增一条门禁；新增 `cli/dev` 的子命令 | 升级不用改配置，多了能力 |
| **patch** | 装配层**行为修正**，对外形状不变：修 bug、改错误信息、改进文案、补测试 | 修 `RepoNotFound` 的错误提示；修热重载不彻底回滚的缺陷 | 升级不用改配置 |

### 2.2 不该动（**不 bump**）的情形 —— 这些是本策略最容易做错的地方

| 情形 | 为什么不动 | 正确的记录位置 |
|---|---|---|
| **某个兄弟仓自己发了版**（worldbuilder / an-engine / 3dworld 任一） | 那是**它们的**版本，与本仓装配层无关 | 兄弟仓自己的 CHANGELOG |
| **兄弟仓版本变了，但 `SUPPORTED_CONTRACTS` 声明的兼容区间没变** | 接缝没变 ⇒ 契约版本不动；装配层也没动 ⇒ 组合仓版本不动 | 本文件无记录（真的什么都没变） |
| **只改了文档 / 注释 / README** | 对外形状零变化 | 本仓 git 历史（`docs:` 前缀的提交） |
| **只改了本仓内部实现**（如 `_locate.py` 的路径解析顺序）而对外行为不变 | 对外形状零变化 | 本仓 git 历史 |
| **只补了测试** | 对外形状零变化 | 本仓 git 历史 |

> **判据浓缩成一句**：**组合仓版本号只在「使用者手里的东西会因此变得不一样」时才动。**
> 「不一样」指配置、命令、契约形状、门禁判据这四类——
> 而不是指「代码变了」。代码变动频率远高于这四类，照代码变动 bump 会让版本号失去信息量。

### 2.3 兄弟仓升级会不会牵动本仓版本？—— 会，但走的是**契约**这条路

这是最容易漏掉的一条链路：

```
兄弟仓改了 bridge 接口的形状（多一个方法 / 改一个签名）
        │
        ├─→ 该契约的兼容性变了 ⇒ 契约版本号可能要动（§3）
        │
        └─→ 若新形状与本仓 `CONTRACT_VERSIONS` 声明的区间不再相容
                ⇒ 装配期会报 `ContractVersionError`（不是运行期才炸）
                ⇒ 此时**必须**动组合仓版本（至少 patch，若需改配置则 minor/major）
```

注意方向：**是接缝不兼容倒逼组合仓发版，不是兄弟仓发版本身倒逼。**
中间如果三仓各自都还在兼容区间内，那组合仓一个号都不必动。

## 3. 契约版本号：独立于一切，且每个契约各算各的

### 3.1 契约版本动的是「接缝形状」，判据与组合仓版本**同源**

| 级别 | 判据 |
|---|---|
| **major** | 该契约的形状**不兼容**地变了：老提供方按老接口实现就装不上了（**含给已有 `Protocol` 加方法 / 改方法名**，见 §3.2 实测）。⚠️ **删方法同样按 major**：此时 `isinstance` 仍为 `True`（装配期静默通过），但消费方按老接口调用会在运行期炸——判据不能只挂在「装不上」这一种机制上 |
| **minor** | **新增一个契约**（该契约自己的号从 `1.0.0` 起算），或方法集合**保持不变**前提下的向后兼容语义扩展。⚠️ 本仓**没有「新增可选方法 = minor」这条路**：给已有 `Protocol` 加方法一律按 **major**（§3.2）——注意「加方法会让装配期失败」**只在老提供方未同步时成立**，协同改动是静默的，但版本判据不变 |
| **patch** | 该契约的**语义澄清**或 bug 修正，方法集合与形状都不变 |

> **为什么契约要独立版本化**（`superengine/contracts/_version.py` 的原话）：
> 三仓各自独立发版。若契约版本跟随某一仓，另外两仓就被那一仓的节奏绑架；
> 若不做版本化，三仓静默漂移，装配期不报错、运行期才炸 —— 这正是整合最容易死的点。

### 3.2 一个**实测确认**的坑：给 `Protocol` 加方法 = 破坏性变更

`runtime_checkable` 的 `Protocol` 在 `isinstance` 判定时**只检查方法存在性**。
实测（2026-11-04）：

```python
@runtime_checkable
class Old(Protocol):
    def a(self) -> int: ...

@runtime_checkable
class New(Protocol):
    def a(self) -> int: ...
    def b(self) -> int: ...

class Impl:                       # 只实现了 a
    def a(self): return 1

isinstance(Impl(), Old)   # True
isinstance(Impl(), New)   # False  ← 老提供方在装配期直接失败
```

⇒ **单边改动**（只给契约加方法、老提供方不动）时，老提供方会在装配期就被
`check_provider` 拒掉，即使那个方法对它们来说完全不影响。
⚠️ **协同改动**（`Protocol` 与三仓 bridge 同步加了方法）装配期是**放行**的 ——
详见下方「两类真空」，别把这句话读成无条件结论。
所以「加个方法算 minor」的直觉是错的：
在本仓的 `isinstance` 判定模型下，**给 `Protocol` 加方法必须按 major 处理**，
除非新方法带默认实现且判定逻辑同步放宽（当前 `check_provider` 走的是裸 `isinstance`，没有这个放宽口子）。

这直接决定了本仓新增契约的做法：**新增契约（新的 `Protocol`）走 minor，
给已有契约加方法走 major**——这也是为什么 `dungeon_source` / `rules_kernel`
当初是作为**两个新契约**加进来（`6cfcbea`），而不是往已有契约里塞方法。

**诚实边界（别把「形状可发现」写成「已闭环」）**：
「加方法 ⇒ 升 major」在本仓目前是**人工纪律 + code review**，不是机械门禁。
`CONTRACT_VERSIONS` 与任何方法名快照之间**没有派生关系**——即便将来补了
方法名集合断言，它**不会**机械强制升版本号。

**根因：装配期门禁是「满足性检查」，不是「差异检查」**。`check_provider` 只问
「**当前**提供方是否满足**当前** `Protocol`」，**从不问**「`Protocol` 相对上一版变了没有」。
所以是否静默**取决于改动是不是协同的**（2026-11-05 实测，证据见下方）：

| 场景 | 装配期 `isinstance` | 结论 |
|---|---|---|
| 单边：加方法 / 改方法名，**老提供方不动** | `False` | `check_provider` **响亮拒绝** |
| 单边：删方法 / 放宽协议 | `True` | **静默通过**（真空 ①） |
| **协同**：`Protocol` 与三仓 bridge **同步加方法**，却忘了升 `CONTRACT_VERSIONS` | `True` | **静默通过**（真空 ②）：`1.0.0 in >=1.0,<2.0` 仍 PASS、`EXPECTED_CONTRACTS` 未变、`test_baseline` PASS ⇒ 全门禁不响 |

⇒ 真空是**两类**，不是一类：① 删方法 / 放宽协议；② 协同加方法（含改名）却忘升版本。
「加方法会被装配期拦住」**只在单边改动时成立**，别写成无条件结论。
两者共同点：**契约形状变了，而 `CONTRACT_VERSIONS` 没跟着动**，装配期无从察觉。

**这条边界的时态**：**两类真空的存在与机理是当前代码的既有事实，不随 A/B 变**
（与 [`已知风险与缓解.md §3`](../architecture/已知风险与缓解.md) 一致：选 A 也保留，
不是待改项）。随 A/B 变的只是它们的**状态标注** —— 选 B 补了方法名集合快照后，
两类形状变更都会从「静默」变成「不再静默」，但快照与 `CONTRACT_VERSIONS`
**无派生关系**，仍**不**机械强制升版本号。⇒ 无论 A/B 怎么裁，只能写
「形状变更不再静默；升 major 仍是人工纪律 + code review」，
**不能**整句翻成「已闭环」或「版本升级已自动化」。
**本节只固定机理、两类真空与粒度边界，不预先宣告「当前哪些还静默」** ——
那是 `已知风险与缓解.md §3` 状态栏的 A/B 裁定项，由 #11 统一写，避免抢跑。

> ⚠️ **两个「B」不是一回事，别混**（#11 汇编易踩）：
> - 本节的 **A/B** = **#11 待决项**：是否补 `EXPECTED_METHODS` 方法名快照
>   （A 只纠文档 / B 补门禁）。**尚未裁定**。
> - 另一个 **「方案 B」已落地** = **契约 bump 判据单一事实源**的选择
>   （design-strategist 定：判据本体留本文 §3，设计层两份压成索引）。
>
> ⇒ 看到「已选 B」时先确认指哪个；**别把「判据单一事实源已选 B」误读成
> 「方法名快照已决定补」**。两者一个是已落地的文档归属，一个是待裁的门禁。
>
> **消歧本体在本文 §3.2，不随其他文档的编排变化**：「方案 A / B」只是团队评审时的
> 选项标签，不是耐久内容。仓内**只应有一个待裁的 `#11 A/B`（方法名快照）**；
> 「判据单一事实源」是**已落地**的判据归属决定，不参与该待裁项。
>
> ⇒ **#11 汇编以磁盘现状为准，不要凭任何一封回执去增删其他文档里的字母代号或消歧块**：
> `docs/design/新增契约流程.md` §2 是否给判据归属起代号、是否保留指路句或第二份消歧块，
> 由该文档维护者自行决定；无论哪种形态，都不改变「一个待裁 A/B + 消歧本体在 §3.2」
> 这条口径，也不改变下面「升 major 仍是人工纪律」的粒度边界。

> **证据强度与测法留痕**：QA 用三态变异体在**真实装配出的 `ctx.tdworld`** 上跑
> `check_provider`：`baseline → ACCEPTED` / `add → REJECTED` / `rename → REJECTED` /
> `remove(empty) → ACCEPTED (silent)`；另以「两侧都新建类」复现协同场景得
> `ACCEPTED (SILENT)`，且 `1.0.0 in >=1.0,<2.0` 与 `EXPECTED_CONTRACTS` 快照均 PASS。

> `CONTRACTS['render_sink'] = ShapeV2` 并**先断言探针自身有效**（注册表用的是变体、
> `isinstance` 与区间断言的实际值）后才拿到可信结果。
> ⇒ **负例探针必须先自证跑到了目标路径，并从实际输出推导结论，禁止在脚本里写死结论**
> （又一例「测法骗人」，判据见 [`发布清单.md`](发布清单.md) §2）。

**这条边界也管 `CHANGELOG.md` 的 `[Unreleased]`**：若最终选 B 补了
`EXPECTED_METHODS`，该段只能记「新增方法名集合的机械断言（覆盖两类真空）；形状变更不再静默」，
**不得**写成「G6 完全闭环」或「契约版本升级已自动化」——
后者需要 `EXPECTED_METHODS` 与 `CONTRACT_VERSIONS` 有派生关系，而本仓没有。
新门禁属 tag 之后的工作，进 `[Unreleased]`，**不回填 `[0.1.0]`**。

### 3.3 区间语义

- 区间串形如 `">=1.0,<2.0"`、`"==1.2.0"`、`">=1.1"`。
- **主版本不同即视为不兼容**（`>=1.0,<2.0` 是最常用写法）。
- 契约版本**必须**落在提供方 `SUPPORTED_CONTRACTS` 声明的区间内，否则**装配期报错**。
- 契约**未被声明**同样报错——静默的「我没这能力」比显式失败更难查。

## 5. 首次发布的版本号：`0.1.0` 合适吗

**结论：合适，建议保留 `0.1.0`，不改。**理由三条：

1. **语义化版本对 `0.x.y` 的定义就是「公开 API 不稳定」**——
   本仓的契约形状已经历过两次扩张（`dungeon_source` / `rules_kernel` 加入），
   装配层的配置面也还在演进（`configs/dev.json` 的键、`cli/dev` 的子命令都是近期才有的）。
   标 `1.0.0` 等于对外承诺「接缝不会再破」，这个承诺现在兑现不了。

2. **本仓是组合仓，用户的第一道坎不是版本号而是「能不能跑起来」**——
   四仓要并排、要装对依赖、要过门禁。此时版本号传达的信号应当是
   「这是一个还在快速演进、但已经能跑的早期版本」，`0.1.0` 恰好是这个意思。

3. **本仓从未发过版**，`0.1.0` 是这个仓库的**第一个**版本号，
   不存在「与前一版对比」的语义负担。

**`0.1.0` 有一个必须同步兑现的前提**：既然标了 `0.1.0`，

## 6. 什么时候该动契约版本而不是组合仓版本

一句话对照：

| 场景 | 动哪个 |
|---|---|
| 改了 `superengine/bridges/` 里的实现细节，对外行为不变 | **都不动** |
| 改了 `superengine/bridges/` 的 `provide` 名 / 注入关系，装配配置要跟着改 | **组合仓 major 或 minor** |
| 改了一个 `Protocol` 的方法签名 | **契约 major**（§3.2）+ 组合仓 major |
| 加了一个新 `Protocol` 并登记进 `CONTRACT_VERSIONS` | **契约 minor**（新契约自己的 `1.0.0`）+ 组合仓 minor |
| 三仓中有一仓改了 bridge 实现，但区间仍相容 | **都不动** |
| 三仓中有一仓改了 bridge 实现，区间不再相容 | **契约 major** + 组合仓 major（须改装配配置） |

> **两套号一起动是常态，但触发点不同**：契约号由「接缝形状」触发，
> 组合仓号由「使用者手里的东西变了没有」触发。
> 前者是后者的**充分条件之一**，不是必要条件——
> 契约 major 一定牵动组合仓 major（老提供方装不上了，装配层必然要改），
> 但组合仓 minor 不一定牵动契约号（加一条门禁、新增一个 CLI 子命令都不碰接缝）。

## 7. 一页速查

```
两套计数器：
  superengine 版本号  ← 装配层变了没有      （pyproject.toml / git tag）
  契约版本号          ← 跨仓接缝变了没有    （CONTRACT_VERSIONS，每个契约一个号）

都不跟随任何一仓的发版。

组合仓 bump 判据（对使用者有没有影响）：
  major  现有配置 / 命令 / 桥接写法不再成立
  minor  向后兼容地扩了能力
  patch  行为修正，对外形状不变

不动组合仓版本号的典型情形：
  兄弟仓自己发版 · 区间没变 · 只改文档 · 只改内部实现 · 只补测试

契约 bump 判据：
  major  形状不兼容地变了（给 Protocol 加方法也算！——见 §3.2 实测）
  minor  向后兼容地扩了（新契约走这条）
  patch  语义澄清 / bug 修正

联动：
  兄弟仓改接口 → 契约号可能动 → 装配期兼容校验 → 不相容则组合仓号必须动
  相容 ⇒ 组合仓号一个都不动。
```
