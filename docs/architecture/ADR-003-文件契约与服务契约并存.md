# ADR-003 · 文件契约与服务契约并存

> 状态：**生效** ｜ 生效日 2026-10-24 ｜ 复核 2026-11-04
> 载体：`worldspec v1` 文件契约、`superengine/contracts/protocols.py` 的
> `WorldSpecSource` / `MapGraphSource`、cordis Service 与 `inject` 依赖图、
> `superengine/live.py`（M3）、`superengine/bridges/terrain_backends.py`（M4）。

## 背景

三仓要协作，有两种天然路径：

* **离线 / 文件**：worldbuilder 把世界落成 `worldspec v1` 目录（JSON 图层 +
  `graph.json` + `meta`），an-engine 读目录建 `MapGraph`。跨进程、可存档、可独立发布。
* **在线 / 服务**：同进程内，worldbuilder 产出 `f(x,z)→h` 采样器，
  3dworld 直接消费生成网格，cordis 管生命周期。

整合时最容易犯的错，是觉得「既然都接进来了，统一成一条路径更干净」——
把文件契约废掉只留服务，或反过来把服务契约全部改成落盘交换。

## 决策

**两条轴并存，不互相替代。** 判据是「这次协作需要跨进程边界吗」：

| 什么时候用哪条 | 选 |
|---|---|
| 存档、跨进程、独立发布、别人拿到目录就能用 | 文件契约（worldspec v1） |
| 同进程在线装配、要热重载、要换实现、要开发循环 | 服务契约（cordis） |

具体保留：

1. `WorldSpecSource.generate / save / load / validate_spec / meta` 管离线；
2. `TerrainSource.make_height_sampler` + `TerrainSink.terrain_mesh` 管在线接缝；
3. `MapGraphSource.mapgraph_from_worldspec` 从文件契约读，
   `GameplayWorld.provide_mapgraph` 把结果挂进被托管的 Context；
4. `DungeonSource.dungeon_graph` 的产物与 `graph.json` **同形** ——
   生成侧与玩法侧共用一套形状，两条轴在数据层面自然对齐。

## 理由

* **worldspec 是「三仓互不引用却仍能协作」的底线**：它让三仓在没有同一进程、
  甚至不在同一台机器上时也能对接。删掉它，三仓就被迫同生共死。
* **服务契约是 M3 / M4 的前提**：cordis `Hmr` 热重载（换 fiber 不泄漏 registry）
  和 `reflect.Impl` 多实现替换（clipmap ⇄ flat，消费方代码一行不改）
  都依赖「能力挂在 Context 上」这件事。改成落盘交换就全没了。
* **坐标解释权归产出方，两条轴一致**：无论走文件还是走服务，
  都是 worldbuilder 定义 `(x, z)` 到高度的映射，3dworld 只消费 `f(x,z)→h`。
  不存在「文件里一套坐标、服务里另一套」。
* **同形复用降低认知成本**：`dungeon_graph` 与 `graph.json` 同形，
  an-engine 的 `MapGraph` 不用为地牢单独写一套解析。

## 备选方案与为何否决

| 备选 | 为何否决 |
|---|---|
| 统一成服务契约（废掉 worldspec v1） | 离线发布 / 存档 / 跨进程没了；三仓被迫同进程，独立性受损 |
| 统一成文件契约（所有交换都落盘） | M3 热重载、M4 换实现、`dev` 常驻会话全废；每次调参都要写磁盘 |
| 只在测试里保留文件契约 | 测试能跑≠产品能用；文件契约是发布形态，不是测试夹具 |
| 让 3dworld 直接读 worldspec 目录 | 3dworld 就要理解 worldbuilder 的磁盘格式，跨仓耦合；现在它只吃 `f(x,z)→h` |

## 后果（代价）

1. **两条路径都要测**：`tests/test_pipeline.py` 既测文件契约链路
   （worldspec → MapGraph），也测在线链路（采样器 → 网格）。少一条就会有
   「一半能跑」的假绿。
2. **同形是约定，不是类型保证**：`dungeon_graph` 与 `graph.json` 同形靠 dict 结构
   对齐，没有 schema 校验器。生成侧改字段名，玩法侧会在运行期才炸。
   这是已知缺口，见 [已知风险与缓解 §4](已知风险与缓解.md)。
3. **`dev` 会话的诚实边界**：`python -m superengine.cli.dev` 只保证
   「三仓 bridge 接口 + 本仓 entry」两层被真正换掉。Python `importlib` 不会
   重绑定其他模块已持有的引用，改更**深的内部模块**建议重启会话。
4. **热重载不泄漏的判据是 registry 规模**：`dev --once` 输出里的 `registry=10`
   是基线；涨了就是「两份逻辑同时跑」。两条轴并存意味着这个判据只在服务轴上有效。
5. **文档要写清「什么时候用哪条」**：判据在
   [`../design/契约体系设计.md` §2](../design/契约体系设计.md)，
   不写清的话下一个人会本能地想「统一一下」。
