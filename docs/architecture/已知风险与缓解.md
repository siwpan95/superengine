# 已知风险与缓解

> 时点：2026-11-04 ｜ 本文是**实测结论 + 明确标注的未验证项**的混合体。
> 每条都写明「已验证到什么程度」。快照型结论会过期，改代码前请复核。

## 1. 🟡 组合仓被迫声明兄弟仓的传递依赖（pyglet）

**状态**：已缓解（依赖已声明），根因仍在，需跨仓改动根治。

### 实测链路

```
superengine/bridges/tdworld_bridge.py
  → _locate.import_bridge("3dworld")
  → world3d.bridge
  → world3d/__init__.py            (from world3d.engine import *)
  → world3d/engine/mathkit.py:19   (from pyglet.math import Mat4, Vec3)
  → pyglet.math
```

2026-11-04 实测：干净机按旧 `requirements.txt`（PyYAML / watchdog / numpy）
装完后 `python -m superengine.cli.boot` 报 `No module named 'pyglet'`，
`tests.run_tests` **只有 1/6 模块通过**（仅不碰三仓的 `test_no_cross_import`）。

### 风险定级：**中**，且边界要划清

| 是风险 | 不是风险（别夸大） |
|---|---|
| **声明面耦合**：pyglet 是 3dworld 的依赖，却成了 superengine 必须声明的东西 | 「headless 跑不起来」——不成立 |
| **版本漂移**：3dworld 若换 pyglet 大版本，`pyglet==2.1.16` 锁可能失配 | 「Linux 必须装整套 X11/GL 库」——对**渲染路径**成立，对**本仓装配路径**不成立 |
| 三仓升级后组合仓要跟着复核依赖清单 | 「本仓用了 OpenGL」——完全没用 |

### 支撑证据（2026-11-04 实测，`sys.modules` 前后差）

```
测 1  from pyglet.math import Mat4, Vec3
      → 加载的 pyglet 子模块: ['pyglet', 'pyglet.math']
      → app/gl: []

测 2  完整装配链路 import world3d.bridge
      → 加载的 pyglet 子模块数: 2
      → ['pyglet', 'pyglet.math']
      → 重量级模块(会拉 X11/GL): []

测 3  pyglet 2.1.16 顶层 __init__.py
      → 含 app 导入: False / 含 gl 导入: False
      → pyglet/math.py 的全部 import: math / typing / warnings（纯标准库，无 ctypes、无 dlopen）
```

⚠️ **这修正了一条跨仓认知**：`3dworld/.github/workflows/ci.yml`（四仓并排时从父目录起算）注释写
「即使开 headless，X11 那几个库也必须装 —— `import pyglet` 会无条件加载 xlib 事件循环」。
该判断对 **pyglet 的渲染路径**成立，但 **pyglet 2.1.16 顶层是懒加载**，
`import pyglet` 本身不碰 app/gl/display/window。superengine 只走 `pyglet.math`（纯 Python）。
⇒ 本仓 CI 的 Linux / macOS job 采用**精简依赖策略**，并让 CI 自己证明；
详见 [`../quality/门禁标准.md`](../quality/门禁标准.md)。

### 缓解（已做）

* `pyproject.toml` 声明 `pyglet==2.1.16`，`requirements.txt` 通过 `-e .` 转发，
  **单一事实来源**，不再两份清单漂移。
* `scripts/bootstrap.py` 显式断言四个依赖模块可 import，把「依赖缺失」与
  「仓没找到」分开报。
* CI 加「依赖自检」step：不重复 `pip install`，只断言 `-r requirements.txt`
  这条链真的把 numpy / pyglet 带进来了。

### 根治建议（**需跨仓改动，本仓不动手**）

先说结论：**原先提的两条候选路径，单独任一条都不成立**。2026-11-04 在 3dworld 的
**temp 副本**上逐项实证（未修改兄弟仓任何文件）。原因是 pyglet 在装配链上有
**两个互不相关的顶层入口**，且都挂在 `world3d/engine/__init__.py` 的无条件导入下：

| 入口 | 位置 | 谁拉它进来 |
|---|---|---|
| ① `from pyglet.math import Mat4, Vec3` | `world3d/engine/mathkit.py:19` | `engine/__init__.py:30` |
| ② `from pyglet.math import Quaternion, Vec3` | `world3d/engine/timeline.py:21` | `engine/__init__.py:36` |

`world3d/bridge.py:20` 自己就写 `from .engine.terrain_clipmap import ...` ——
导入任何 `.engine.*` 子模块**必然先执行** `engine/__init__.py`。所以「去掉
`world3d/__init__.py` 的星号转发」切不断这条链（实测：换成空包壳 + 屏蔽 pyglet，
`import world3d.bridge` 仍加载 `pyglet.math`）。此外 `engine/__init__.py` 还经
`texproj → geometry → mathkit` 二次抵达 ①。

**实验矩阵**（用 meta_path finder 完全屏蔽 pyglet，等价于「干净机没装」）：

| 改动（仅 temp 副本） | `import world3d.bridge` |
|---|---|
| 原样 | ❌ `ModuleNotFoundError: pyglet` |
| 只去掉 `world3d/__init__.py` 星号转发 | ❌ 同上 |
| 只把 `mathkit` 改纯 Python | ❌ 同上（② 还在） |
| 只把 `mathkit` 改函数内懒加载 | ❌ 同上（② 还在） |
| ① ② 都改函数内懒加载 | ✅ import 通过（但 `timeline` 运行时语义破了，见下） |
| ① ② 都改纯 Python 同形替代 | ✅ import 通过 + 运行时语义保住（负例：`Mat4` 返回类型变了，渲染路径有风险） |
| ① ② 都改 try/except 惰性降级 | ✅ import 通过 + 有 pyglet 时语义不变 |

⚠️ **「懒加载」不是免费午餐**：`Mat4` / `Vec3` / `Quaternion` 在
`mathkit.py` / `timeline.py` 的函数体里是**模块全局名**（`isinstance(v, Quaternion)`、
`_from_comp()` 构造等十余处）。

* 用 **PEP 562 模块级 `__getattr__`**：只能让 import 通过，函数内全局名**不走**
  `__getattr__`，实测 `mat4_to_Mat4()` / `_from_comp()` 调用期抛 `NameError`。
* 用**函数内局部 import**：`mathkit` 只有 3 处能补完，但 `timeline` 十余处
  分散在多个函数里（还有 `isinstance` 判断），实测只补一处 import 行的形态下
  `_is_quat()` / `_from_comp()` 仍抛 `NameError`。

所以「把 import 挪个位置」既不是一行改动，也容易留下「import 成功、一调用就炸」
的假绿 —— 这正是本仓门禁最忌讳的形态。

#### 推荐方案：① ② 两处 try/except 惰性降级，**不是**纯 Python 重写

`mathkit.py:19` / `timeline.py:21` 各改成
`try: from pyglet.math import ... / except ModuleNotFoundError: <名字> = None`
（更好是给一个显式报「缺 pyglet」的哨兵函数），其余代码一行不动。

* **为什么不推荐「纯 Python 重写」**：3dworld 本来就**是** pyglet 渲染引擎
  （`engine/__init__.py` docstring 自述「数学用 pyglet.math，绘制用 pyglet.gl」）。
  本仓要解决的不是「3dworld 依赖 pyglet」，而是「**headless 消费方被强制装渲染依赖**」。
  纯 Python 重写会把 `mat4_to_Mat4()` 的返回类型从 `pyglet.math.Mat4` 换成自研类型，
  而 `renderer.py` / `mesh.py` / `app.py` / `skin.py` / `camera.py` / `csm.py`
  都拿它喂 pyglet uniform 或 `window.view` —— 那是 3dworld 的**主渲染路径**，
  风险远大于收益。惰性降级在「有 pyglet」时语义 100% 不变。
* **实测能达成目标**：pyglet 屏蔽 + `TDWORLD_SRC` 指向 temp 副本时，superengine
  5 个 fiber 全 ACTIVE，M1 流水线产出 5120 顶点 / 5 ring / 高度 0.235~0.732。
  即方案落地后本仓可**真的删掉 pyglet 声明**，而不是只把 import 挪个位置。
* **影响面**：3dworld 侧 2 个文件、各 1 处 import；不改函数签名 / 返回类型 / `__all__`；
  渲染路径在有 pyglet 时零变化。唯一新增失败模式是「无 pyglet 却调用了那几个转换
  函数」，应显式报错，别留成 `TypeError: 'NoneType' object is not callable`。
* **需单独提 PR**：改的是独立仓 3dworld，有自己的发版节奏与「本仓不吞并」纪律
  （ADR-002 决策 5）。该 PR 必须带 3dworld 全量回归（**含真窗口 demo**），不能只跑
  superengine 的 headless 门禁。合入并发布后，本仓再开一个 PR 删除
  `pyproject.toml` 的 `pyglet==2.1.16`、同步 `requirements.txt` 注释、
  `scripts/bootstrap.py` 依赖自检与 CI 依赖自检 step —— **两仓两步，不要同一次提交**。

**保留项**：跨仓 PR 落地前，`pyglet==2.1.16` 继续声明；本轮不修改兄弟仓任何文件。

## 2. 🟡 热重载只保证「bridge 接口 + 本仓 entry」两层

**状态**：已如实声明，属 Python 语言限制，无根治方案。

`importlib` **不会重绑定其他模块已持有的引用**。所以 `dev` 会话（M3 + M4）
只保证这两层被真正换掉；改了某个仓的**内部**模块，已 import 它的对象仍指向旧代码。

**缓解**：README 的「诚实边界」段 + `devloop.py` docstring 明写；
文档建议「改更深的内部模块就重启 `dev` 会话」。监听用轮询（默认 0.5s）而非
后台线程，确定性更好、测试可直接调 `tick()`。

**残留**：使用者不看文档时会以为「改了没生效」是 bug。

## 3. 🟡 契约形状变更 vs 三仓区间声明，缺机械门禁

**状态**：**部分缓解（2026-11-04 G6 落地）**；「形状变更 → 必须升版本」仍无门禁。

`check_provider()` 在**装配期**验区间与结构，能挡住「已装的三仓不兼容」。
但它挡不住「有人给 `Protocol` 加了方法却忘了升 `CONTRACT_VERSIONS`」——
因为 `@runtime_checkable` 的 `isinstance` 只查方法存在性，加方法会让老提供方
在装配期被拒（实测 `isinstance(Impl(), New)` 返回 `False`），**这反而算一种迟到拦截**。

**已缓解的部分（G6）**：`tests/test_assembly.py` 新增三条机械断言，把
「契约版本 → 三仓声明区间」的对照固化：

| 断言 | 守什么 |
|---|---|
| `test_three_repo_declared_contract_names_are_registered` | 三仓声明的契约名都在注册表里（防拼错 / 幽灵契约） |
| `test_registry_versions_fit_three_repo_intervals` | 注册表每个契约的版本落在**声明它的**三仓区间内（反向，装配期之外就红） |
| `test_all_registry_contracts_have_a_provider` | 注册表不得出现三仓谁都没声明的孤儿契约（`check_all` 的方向查不出） |

三条都复用 `_version.py` 的 `version_in_interval` / `parse_interval`，不另写版本算术；
三仓任一缺失时**打印具体仓名与修复指引后 skip**（测试函数本身不伪造断言结果），
但模块级判定改为 `ALL_ASSEMBLY_TESTS_INCOMPLETE` 并返回 1 —— 让聚合 runner
判 `[FAIL]`，而不是「联动断言一条没跑却报绿」。CI 四仓并排布局下不 skip。
三条均已用负例验证确实会红（拼错名 / 升到 2.0.0 不同步 / 孤儿契约）；
skip 假绿面由 QA 于 2026-11-05 实测发现并复验消除。

### 一条方法学残留：**负例探针必须验证「探针自己跑到了」**

「断言会红」被验证了，但「**聚合 runner 的判定公式会不会把红判成绿**」是另一层。
2026-11-05 两侧各踩了一次**测法骗人**（不是被测对象骗人）：

* 本仓用 `sitecustomize` 注入钩子复现 skip 场景，`python -m` 却把目标模块当
  `__main__` 执行，钩子改的是 `tests.test_assembly` 这个**另一个 module object**，
  测出的 `[PASS]` 是假的；改用「子进程直接调用 `main()` 本体 + 套判定公式」才可信。
* QA 侧第一版用嵌套 `python -c` 注入，引号转义把脚本弄坏，三行 `VERDICT` 全空；
  改成进程内 monkeypatch + 直接调**真实 `run_tests.main()`** 才拿到结果。

⇒ **四次都是探针没真正跑到 / 建模无效，而不是门禁判错**。写负例的可执行纪律：
1. 先断言探针自身有效（期望值 / 计数 / 非空输出），再看被测结论；
2. **结论必须从实际输出推导，禁止写死** —— QA 有一版脚本硬编码了
   「=> ALL gates pass; silent」而实际输出是 `REJECTED`；
3. **验证契约形状类断言必须新建 `Protocol` 类**，不能就地增删方法：
   Python 3.12+ 在类创建时把方法集合缓存进 `__protocol_attrs__`
   （本机 3.13.14 实测 `ShapeV1.__protocol_attrs__ == {'terrain_from_heightfield'}`），
   运行时 mutation 不刷新，`isinstance` 看到的还是旧形状；
4. **建模「协同改动」必须两侧（Protocol 与提供方）都重建类**，只改一侧
   得到的是「单边改动」，是另一条路径；也不要在 `Traceable` 实例上塞属性
   （`setattr` 转发 + 缓存 ⇒ 无效建模）。

**判定公式现在是对的，别把这条当缺陷修**：QA 独立 monkeypatch 注入
`run_tests.MODULES` + `subprocess.run`、直接调真实 `run_tests.main()`，
`rc == 0 and marker in out` 三个方向全部正确：
```
rc0_no_marker  expect=FAIL got=FAIL OK
rc1_has_marker expect=FAIL got=FAIL OK
rc0_has_marker expect=PASS got=PASS OK
```
所以这属于 **P2 预防性回归断言**——防的是将来有人把判据削弱成「只看 rc」
或「只看 marker」，不是「现在有 bug」。是否落地为 `run_tests.py --self-test`
由 QA / 主理人在 full 评审定；**不新开第 9 个模块**（8/8 正在汇编，加模块
会让文档数字再漂一次，收益不抵成本）。

另：`ALL_ASSEMBLY_TESTS_INCOMPLETE` 与 `rc=1` 是**一对判据，不能拆开** ——
只留新尾标记而返回 0，或只改返回码而仍打 `PASSED`，都会重新打开假绿面。

**仍未缓解**：契约**形状变更但版本号没升**没有机械门禁。`test_baseline.py`
的快照锁的是契约名 / 版本号与「至少有一个方法且只含方法」，**不锁方法名集合**。
2026-11-05 用真实 `check_provider` 做变异体实测，`@runtime_checkable` 只查
「协议声明的方法是否都在对象上」，结果分**单边改动**与**协同改动**两组：

| 场景 | `check_provider` | 说明 |
|---|---|---|
| 单边：只给协议加方法 / 改方法名，老提供方不动 | **REJECTED** | 老提供方缺新方法，装配期响亮拒绝（迟到但拦得住） |
| **删方法 / 放宽协议** | **ACCEPTED（静默）** | 老提供方仍满足更弱的协议 —— **真空 ①** |
| **协同：协议与三仓 bridge 同步加方法，却没升 `CONTRACT_VERSIONS`** | **ACCEPTED（静默）** | `1.0.0` 仍落在 `>=1.0,<2.0` 内、契约名未变 ⇒ G6 三条联动断言与 `EXPECTED_CONTRACTS` 快照全部 PASS，全仓无断言会红 —— **真空 ②** |

真空 ② 正是「契约版本与形状脱钩」，也正是「契约独立版本化」要防的核心情形；
早先只写「唯一真空是删方法」是**把残留面写窄了**（只建模了单边改动）。

⇒ 两类真空都靠 `docs/design/新增契约流程.md` 的人工步骤 + code review 兜，
没有机械断言。若 #11 选 B 落地 `EXPECTED_METHODS` 快照，**两类真空都会被逼出
显式确认**（方法名集合变了 ⇒ 快照红），收益比只闭一类更大；但**闭合的只是
「静默」面**（形状变更不再无声）—— 快照与 `CONTRACT_VERSIONS` 无派生关系，
**不**强制「加方法须按 major 升版本」，那一半仍是人工纪律 + code review。
⇒ 选 B 后本条应从「仍未缓解」**外科式收窄**为「部分缓解（形状面已闭环，
版本联动仍靠人工）」，级别维持 🟡 中，不写「已闭环 / 已自动化」；
**选 A 则状态栏一字不动**（§3 开头、总览表第 3 行、`ADR-001` 后果 2）。
注意「两类真空」是**当前代码的既有事实，不随 A/B 变** —— 上面这段实测与
真空 ①② 已经落定，选 A 也保留，不是待改项；A/B 只决定状态栏怎么写。

## 7. 🟡 双远端分叉与「只信 ls-remote」

**状态**：流程已固化，风险常驻。

本仓有 gitee `origin`（主）与 github `github`（mirror）两个远端，用户名不同
（`siwpan` vs `siwpan95`）。`git push` 的输出会打印 URL，但**不代表推到了你以为的仓**；
`origin/master` 是缓存，会因 URL 直推而过期。

**缓解**：`docs/release/发布清单.md` 规定——推前 `git fetch` + `git ls-remote`
**两端远端**对比本地 HEAD，确认无分叉再推；推后同样用 `ls-remote` 复核 IN_SYNC。
按中文路径过滤 git 输出必须带 `-c core.quotepath=false`。

另：本机到 GitHub 的直连可用性是**时点事实**（3dworld CI 注释记「断」，
2026-11-04 本会话实测 `curl https://github.com` → 200、`ssh -T git@github.com` 认证成功）。
2026-11-04 当时默认仍按 Gitee 镜像（最短 5 分钟）走，因为镜像路径更稳、且不依赖直连通路。
⇒ **2026-11-05 实测证伪**：该镜像 7 天未生效（GitHub `pushed_at` 停在 2026-10-29、
无 tag、无 `ci.yml`、Actions `total_count: 0`），已改为 **SSH 直推 GitHub**
