# 架构总览 —— superengine 的四层职责与跨仓边界

> 本文描述**2026-11-04 实测**的仓库现状，不是规划稿。想改架构前先读
> [ADR 索引](ADR-README.md) 与 [已知风险与缓解](已知风险与缓解.md)。
> 契约体系的设计语义见 [`../design/契约体系设计.md`](../design/契约体系设计.md)。

## 0. 一句话定位

superengine 是**组合仓**：把 `worldbuilder` / `an-engine` / `3dworld` 三个**独立、
平等、各自发版**的仓，通过 cordis 装配成一条流水线，**但不吞并它们**。

本仓只做四件事：**契约、桥接、装配、门禁**。不含任何算法。

判断「某段逻辑该放哪」的判据很简单：**它是三仓之间的接缝，还是某个仓内部的事？**
接缝归本仓，内部归那个仓自己。

## 1. 四层职责

| 层 | 目录 | 职责 | 依赖边界 |
|---|---|---|---|
| 契约层 | `superengine/contracts/` | 8 个 `@runtime_checkable` Protocol、独立版本号、兼容区间算术、提供方双校验 | **零依赖**（只 import `typing` / `re`），不 import cordis、不 import 三仓 |
| 桥接层 | `superengine/bridges/` | 把三仓能力挂成 cordis Service；**唯一允许 import 三仓的地方** | 穿透到三仓，承担传递依赖（含 pyglet） |
| 装配层 | `superengine/assembly.py` | 白名单 → 预导入 → Loader → 终态 ACTIVE 断言 | 依赖 cordis |
| 门禁层 | `tests/` + `selfcheck.py` | 装配门禁、三仓互不引用扫描、回归基线、契约层无头自检 | 独立，可无头跑 |

另有两处横切：`superengine/_locate.py`（**唯一处理路径的地方**：cordis 与三仓源码定位）、
`superengine/cli/`（boot / dev 两个 headless 入口）。

### 1.1 为什么把路径解析收在一个文件

组合仓要区分两件事：**cordis 是框架**（3dworld 已 vendor 一份纯 Python 移植，
无 pip 发行），**三仓源码是被整合的能力源**（各自独立发版）。
把解析逻辑集中在 `_locate.py`，桥接插件就只写业务、不复制 try/except 兜底；
换部署形态（pip 安装 / 目录并排 / CI）只改这一处。

定位优先级：

```
cordis      : import cordis → $CORDIS_SRC → ../3dworld/vendor/cordis/src
worldbuilder: $WORLDBUILDER_SRC → ../worldbuilder
an-engine   : $ANENGINE_SRC     → ../an-engine
3dworld     : $TDWORLD_SRC      → ../3dworld
```

⚠️ **目录名 ≠ 包名**：目录叫 `3dworld` / `an-engine`，内部包是 `world3d` / `allin_engine`。
自动定位按**目录名**找，所以 clone 时不能改目录名。

## 2. 与三仓的边界

```
  ┌────────────────────────── superengine（本仓） ──────────────────────────┐
  │  contracts/        bridges/          assembly.py       tests/           │
  │  8 Protocols  ←→  3 个 Service  ←──  cordis Loader  ←── 三道门禁         │
  └───────┬──────────────┬──────────────────┬─────────────────────────────┘
          │ 契约形状      │ bridge 友好接口   │ 装配期校验
          ▼              ▼                  ▼
  ┌───────────────┐ ┌──────────────┐ ┌────────────────────┐
  │ worldbuilder  │ │  an-engine   │ │      3dworld       │
  │ 世界生成      │ │ 玩法/规则内核│ │  表现 / 渲染 / 引擎│
  │ 纯 numpy      │ │ 零第三方依赖 │ │  pyglet + numpy    │
  │ worldspec v1  │ │ Context 托管 │ │  headless bridge   │
  └───────────────┘ └──────────────┘ └────────────────────┘
```

三仓**互不 import**（`tests/test_no_cross_import.py` 机械保证）。
它们能协作只因为：① 各自实现契约形状 ② 通过本仓的 `bridges/` 被装配到同一进程。

## 3. 数据流

```
worldbuilder.generate(w,h,seed) → world dict
   ├─→ worldbuilder.save(...) → worldspec v1 目录（离线 / 跨进程 / 独立发布）
   │       └─→ an-engine.mapgraph_from_worldspec(spec_dir) → MapGraph
   │              └─→ an-engine.provide_mapgraph(ctx, graph) → 玩法世界
   │
   └─→ worldbuilder.heightfield(world) → 高程阵列
          └─→ worldbuilder.make_height_sampler(hm, tile_m) → f(x,z)→h
                 └─→ 3dworld.terrain_mesh(height_fn, ...) → 网格（headless，零 GL）
```

两条正交的协作轴（详见 [契约体系设计 §2](../design/契约体系设计.md)）：

| | 文件契约（worldspec v1） | 服务契约（cordis） |
|---|---|---|
| 场景 | 离线 / 跨进程 / 独立发布 | 同进程在线装配 |
| 载体 | 磁盘上的 JSON + 图层 | Context 上的 Service |
| 坐标解释权 | 产出方（worldbuilder） | 产出方（同一份 `f(x,z)→h`） |
| 谁保证 | `validate_spec` / `meta` | `inject` 依赖图 + 终态 ACTIVE |

**两条并存、不互相替代**：需要存档或跨进程时走文件契约；需要热重载 / 换实现时走服务契约。

## 4. cordis 依赖注入图

`configs/cordis.super.yml` 的**书写顺序不决定挂载顺序**，由各 Service 的 `inject` 决定：

```
Loader ─┐
isolate ─┴─→ WorldbuilderBridge  ACTIVE  inject=[]
                    │
                    ├──→ TdworldBridge  ACTIVE  inject=['worldbuilder']
                    └──→ AnengineBridge ACTIVE  inject=['worldbuilder']
```

（`dev` 会话还会额外挂 `TerrainBackendHost` / `TerrainConsumer` / `TimerService` / `Hmr`，
`registry` 基线为 10。）

## 5. 三道装配门禁（治 cordis 已记录的坑）

| 门禁 | 治什么 | 不做的后果 |
|---|---|---|
| entry `name` 白名单 | cordis 把 entry `name` 当模块 import ⇒ 等同执行代码 | 配置里一个名字就能执行任意代码 |
| 装配前手工 `import` | cordis Loader **会吞掉插件构造期异常**（只表现为「服务不就绪」） | 真实异常被吞，排障只能靠猜 |
| 终态断言 ACTIVE | **PENDING 静默**：依赖名拼错不报错、一直等 | 进程可能静默退出，看起来像「跑完了」 |

外加一道 `tests/test_no_cross_import.py`：防止某天有人图省事跨仓 import，
让三仓从「可独立发布」退化成「一损俱损」。

## 6. 里程碑与能力面

| 里程碑 | 能力 | 判据 |
|---|---|---|
| M1 | 补断腿：worldbuilder → 3dworld 接通 | 表现层能消费高程产出网格 |
| M2 | 玩法托管：an-engine 的 `Context` 被**托管**（非替换） | an-engine 保持零第三方依赖、既有测试基线不受影响 |
| M3 | cordis `Hmr` 热重载 | **registry 规模不增长**（否则是「两份逻辑同时跑」） |
| M4 | `reflect.Impl` 多实现可替换 | clipmap ⇄ flat 可换，消费方代码一行不改；不合格实现被拒（PENDING，不崩） |
| M3/M4 → 日常 | `python -m superengine.cli.dev` 常驻会话 | 改配置 / 改 bridge 源码，地形就地重建，不重启进程 |

## 7. 怎么跑

```bash
python scripts/bootstrap.py                 # 一键引导（四仓 + cordis + 依赖 + 自检）
python scripts/bootstrap.py --check-only    # 只体检
python selfcheck.py                         # 契约层无头自检（不依赖 cordis / 三仓）
python -m superengine.cli.boot --report     # 装配 + 门禁 + 契约版本报告
python -m tests.run_tests                   # 全量回归
python -m superengine.cli.dev --once        # 开发循环构建一次
```

CI 与门禁标准见 [`../quality/门禁标准.md`](../quality/门禁标准.md)；
发布面见 [`../release/README.md`](../release/README.md)。
