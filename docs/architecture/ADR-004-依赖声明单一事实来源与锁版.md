# ADR-004 · 依赖声明单一事实来源与锁版策略

> 状态：**生效** ｜ 生效日 2026-11-04 ｜ 复核 2026-11-04
> 载体：`pyproject.toml` 的 `[project].dependencies`（唯一清单）、
> `requirements.txt` 的 `-e .` 转发、`scripts/bootstrap.py` 的依赖自检、
> `tests/test_baseline.py` 的声明面断言、CI 的「依赖自检」step。

## 背景

2026-11-04 干净机复现实测：按旧清单（`PyYAML` / `watchdog` / `numpy`）装完依赖后，
`python -m superengine.cli.boot` 报 `ModuleNotFoundError: No module named 'pyglet'`，
`tests.run_tests` **只有 1/6 模块通过**。原因不在本仓自己的代码里 —— 本仓
`superengine/` 只直接 import `yaml`；真正的依赖是**穿过桥接层**进来的：

```
superengine/bridges/tdworld_bridge.py → world3d.bridge
  → world3d/__init__.py → world3d/engine/__init__.py
  → engine/mathkit.py:19  + engine/timeline.py:21  → pyglet.math
```

这条链解释了两个容易被混为一谈的问题：

1. **为什么组合仓要声明兄弟仓的依赖**：三仓是并排 checkout、不是 pip 发行，
   pip 不会替它们解析依赖；而 `bridges/` 会把它们的 `bridge` 模块**导入同一个
   解释器**，于是三仓（与 vendored cordis）的顶层 import 全都成了本仓环境的硬需求。
   谁装？只能是组合仓。`PyYAML` / `watchdog` 来自 vendored cordis，
   `numpy` 来自 worldbuilder 与 3dworld，
   `pyglet` 来自 3dworld 的 `mathkit` / `timeline`。
2. **为什么「两份清单」是病根**：此前 `requirements.txt` 与 `pyproject.toml`
   各写一份，必然漂移。3dworld 2026-10-29 的 `numpy` 漏声明是同一类事故
   （连「单仓自己的依赖」都能漏），组合仓只会更容易漏 —— 因为漏的那个包
   连「本仓代码 import 过」都不成立，静态扫本仓源码根本发现不了。

`pyglet==2.1.16` 的锁版不是随手挑的，它回答的是「**跟谁锁**」：
3dworld 的 `pyproject.toml` 就锁 `pyglet==2.1.16`；它另有
`requirements-pyglet1x.txt`（`pyglet==1.5.30`，cocos2d 兼容备用路线）。
本仓走默认 2.x 路线，**不拉 1.x 那份**。

## 决策

1. **`pyproject.toml` 的 `[project].dependencies` 是唯一事实来源**，
   四个依赖集中在此：`PyYAML>=6.0,<7` / `watchdog>=4.0,<7` /
   `numpy>=2.0` / `pyglet==2.1.16`。
2. **`requirements.txt` 只保留 `-e .` 一行转发**（其余全是注释），与
   `pip install -e .` 等价。保留这个文件是为了兼容既有文档与 CI 里
   `pip install -r requirements.txt` 这条调用链。
3. **`pyglet` 用 `==` 精确锁版，不用 `>=` 区间**，且与 3dworld 的锁逐字一致。
4. **门禁不重复装依赖、只断言**：`scripts/bootstrap.py`、
   `tests/test_baseline.py`、CI 的「依赖自检」step 都只检查
   `-r requirements.txt` 这条链**真的把包带进来了**，不写第二份 `pip install`。
5. **「何时升级」的判据写死在这里**（留给下游读者，不靠口头约定）：
   只有**同时**满足以下三条，才允许改 `pyglet==2.1.16`：
   * (a) 3dworld 的 `pyproject.toml` 先改了它的 pyglet 锁版并已发布；
   * (b) 本仓在**三平台 CI** 上实跑 `import world3d.bridge` + 全量回归通过；
   * (c) 本仓 `pyproject.toml` 的锁版与 3dworld 的新锁**逐字一致**。
   单方面升级 = 两个仓解析出不同 pyglet 版本，`Mat4` / `Vec3` 语义可能漂移
   （`mathkit.py` docstring 自己记过 pyglet 2.x 过渡版 `Vec3.cross` 改名的坑）。
   若要彻底解除这条耦合，走 [已知风险与缓解 §1「根治建议」](已知风险与缓解.md)
   的跨仓 PR；**PR 落地前不要提前解锁**。

## 理由

* **一份清单只可能错一处**：两份清单漂移是已实证的事故类型，收敛后至少
  「漏声明」会在一个地方被一次性发现，门禁也能一次性断言全。
* **`==` 而非 `>=`**：组合仓与兄弟仓必须解析出**同一个** pyglet 版本。
  区间会让两边在不同时间、不同机器上装出不同小版本，而本仓对 pyglet 的
  依赖是「3dworld 那边 import 期要用」，不是「本仓自己要用」——
  没有本仓侧的兼容性判断依据，唯一可靠的依据就是 3dworld 的锁。
* **`-e .` 不写第二份清单**：`-r requirements.txt` → `-e .` → 读
  `pyproject.toml`，一条链、一个源头。且 `pip install .`（非 editable）
  同样能拿到 `Requires-Dist`，wheel 元数据与源码仓不脱节。
* **不进 `pyglet 1.x` 备用路线**：那是 3dworld 为 cocos2d 兼容单独留的；
  本仓的装配链只走 2.x 的 `pyglet.math`。引入 1.x 会凭空多一条
  未经回归的分支。
* **依赖范围按用途分层**：cordis 的 `PyYAML` / `watchdog` 用 3dworld 同源的
  区间（vendored 代码标 optional extra、实为硬依赖）；`numpy>=2.0` 取
  worldbuilder（`>=1.24`）与 3dworld（`>=2.0`）的**交集上界**，保证一个
  环境同时满足三仓。

## 备选方案与为何否决

| 备选 | 为何否决 |
|---|---|
| 继续维护两份清单，靠人工「记得同步」 | 已实证会漂移；且漏的那个包本仓源码根本没 import，静态扫不出来 |
| `pyglet>=2.1` / `pyglet>=2.1.16` 区间 | 与 3dworld 的精确锁脱钩，两仓可能解析出不同版本；`Mat4`/`Vec3` 语义跨版本变过，风险不可控 |
| `pyglet==2.*` 兼容 release | 同上；且 pip 不支持这种通配写法，实际会退化成 `>=` |
| 把 3dworld 的 `requirements-pyglet1x.txt` 也拉进来 | 那是 3dworld 的 cocos2d 兼容备用路线，与本仓装配链无关，凭空增加未回归分支 |
| 用 `dynamic = ["dependencies"]` 让 `pyproject.toml` 反向读 `requirements.txt` | 实测可行（setuptools ≥ 63 支持 `tool.setuptools.dynamic.dependencies = {file=[...]}`，注释/标记能解析，sdist 会带 `requirements.txt`）。但本仓选 `-e .` 方向，理由是：让**包元数据**做权威源，`pip install .` 与 `pip install -r` 都读它；且 3dworld 已采用同一形态，四仓保持一种心智模型。代价见「后果 3」 |
| 干脆不声明 pyglet，让使用者自己装 | 正是本次 P0 事故；干净机按文档装完跑不起来，发布门禁判定「按 README 装完能跑」不通过 |
| 在组合仓里 vendored 一份纯 Python `mathkit` 替代 | 出现两份逻辑，漂移必然发生；且违背「本仓不含任何算法」。根治只能在 3dworld 侧做 |

## 后果（代价，不是收益）

1. **组合仓被迫持有兄弟仓的传递依赖**：3dworld 换 pyglet 大版本时，
   本仓的 `==2.1.16` 锁可能失配，必须按「决策 5」的三条判据同步升级；
   三仓任何一仓升级依赖，组合仓都要复核清单。见
   [已知风险与缓解 §1](已知风险与缓解.md)。
2. **声明面耦合 ≠ 渲染层依赖**：本仓只走 `pyglet.math`（纯 Python，
   实测 `import world3d.bridge` 只加载 `pyglet` / `pyglet.math` 两个子模块，
   不碰 app/gl/display/window），**不需要 X11 / GL 系统库**。
   别把「声明了 pyglet」误读成「本仓要开窗口」；3dworld 的渲染路径才需要。
3. **`-e .` 有两个已知的边界**：
   * 它是**相对当前工作目录**解析的（2026-11-04 实测：从别的目录执行
     `pip install -r /abs/path/requirements.txt` 会报
     `does not appear to be a Python project`）。所以 bootstrap 与 CI 都
     **从仓根执行**这条命令；跨目录调用不是支持的用法。
   * 它会触发一次 PEP 517 editable 构建（需要 build backend 与网络），
     比「纯装四个 wheel」多一步。换来的好处是包元数据与源码仓不脱节。
4. **`requirements.txt` 里不能塞 pip 专有语法**（`-r other.txt` /
   `--index-url` / 环境标记之外的选项）：这些行会被 `-e .` 之外的路径
   误读，也会让「本文件只有一行有效依赖」这条断言失效。
   `tests/test_baseline.py` 已把「只有 `-e .` 一行」固化成断言。
5. **删依赖要等跨仓 PR**：真正解除 pyglet 耦合须改 3dworld 的
   `mathkit.py` + `timeline.py`（两处，单独一处不够，实测见
   [已知风险与缓解 §1](已知风险与缓解.md)）。该 PR 合入发布前，
   本仓不得提前删除 `pyglet==2.1.16`；删除时须同步
   `requirements.txt` 注释、`scripts/bootstrap.py` 自检、CI 依赖自检 step
   与 `tests/test_baseline.py` 的 `MODULE_OF` —— **一次改动改四处**，
   这也是「单一事实来源」只解决了**清单**、没解决**引用点**的残留成本。
