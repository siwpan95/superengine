# ADR-001 · 契约独立版本化

> 状态：**生效** ｜ 生效日 2026-10-24 ｜ 复核 2026-11-04
> 载体：`superengine/contracts/__init__.py` 的 `CONTRACT_VERSIONS`、
> `superengine/contracts/_version.py` 的区间算术、各仓 `SUPPORTED_CONTRACTS`、
> `check_provider()` 的装配期双校验。

## 背景

三个兄弟仓**各自独立发版**：worldbuilder / an-engine / 3dworld 有自己的版本号、
自己的节奏，彼此不引用。但组合仓要在装配期回答一个问题：

> 眼前这个仓提供的能力，形状还是我契约里写的那个吗？

如果契约版本跟着某一仓走，另外两仓就被那一仓的节奏绑架；
如果完全不做版本化，三仓会静默漂移，装配期不报错、**运行期才炸** ——
这正是整合最容易死的点。

还有一个容易忽略的粒度问题：本仓有 **8 个契约**（`worldspec_source` /
`terrain_source` / `mapgraph_source` / `gameplay_world` / `terrain_sink` /
`render_sink` / `dungeon_source` / `rules_kernel`），它们是 8 条独立的跨仓接缝，
变更频率根本不同。

## 决策

1. **契约版本由组合仓独立管理**：`CONTRACT_VERSIONS: dict[str, str]` 是**唯一权威**，
   每个契约一个三段语义号 `MAJOR.MINOR.PATCH`，不跟随任何一仓发版。
2. **各仓声明兼容区间**：`SUPPORTED_CONTRACTS` = `{契约名: 区间串}`，
   区间串形如 `">=1.0,<2.0"` / `"==1.2.0"` / `">=1.1"`。
   区间语义：**主版本不同即视为不兼容**。
3. **装配期校验，不留到运行期**：`check_all()` 逐个取 `supported` 的键，
   到 `versions` 里查版本、验区间；契约未被声明同样报错
   （静默「我没这能力」比显式失败更难查）。
4. **版本 + 结构双校验**：`check_provider()` 先验区间，再对每个声明的契约做
   `isinstance(obj, Protocol)`；不兼容抛 `ContractVersionError`，fiber 进 FAILED。

`check_all` 的方向**不能反**：`supported` 是「该仓能提供什么」，`versions` 是
「契约现在是什么版本」。只查该仓自己声明的契约，**不反过来要求它满足全部 8 个契约**
——否则每个仓都得实现所有能力，三仓分工就没了。

## 理由

* **解耦发版节奏**：worldbuilder 发 0.9.0 不会逼 3dworld 跟着动。
* **漂移在装配期可见**：不兼容直接 `FAILED` 并列出区间，而不是运行到一半
  `AttributeError`。
* **粒度对齐现实**：8 条接缝各自可独立演进，加 `dungeon_source` 不需要动
  `terrain_sink` 的号。
* **零依赖的边界画在 `contracts/`，不是整仓**：`contracts/protocols.py` 只 import
  `typing`，`contracts/_version.py` 只 import `typing` / `re`，所以三仓能各自独立
  引用契约而不触发对另两仓的依赖（这条边界由 `tests/test_baseline.py` 机械断言）。
  但**整仓绝非零依赖**：`assembly.py` import `yaml`，`bridges/` 经三仓 bridge
  穿透到 vendored cordis 的 PyYAML / watchdog、worldbuilder 的 numpy，以及
  3dworld 的 `pyglet.math`（见 [ADR-002 后果 2](ADR-002-桥接层独占跨仓导入.md)）。
  写文档时说「本仓零依赖」是错的；正确说法是「**契约层**零第三方依赖」。

### 一个实测确认的推论：给 Protocol 加方法 = 破坏性变更

`@runtime_checkable` 的 `isinstance` **只查方法存在性**。给已有契约加一个方法后，
老提供方 `isinstance(Impl(), New)` 返回 `False`，装配期被 `check_provider` 拒掉。
所以「加个方法算 minor」的直觉在本仓是**错的**，必须按 major 处理。

这解释了为什么 `dungeon_source` / `rules_kernel` 当初是作为**两个新契约**加进来，
而不是往已有契约里塞方法——新契约不影响任何已声明的区间。

## 备选方案与为何否决

| 备选 | 为何否决 |
|---|---|
| 契约版本跟随 worldbuilder 发版 | 另外两仓被绑架；worldbuilder 改个内部实现也要全组合重新声明；且 8 条接缝里只有 3 条归 worldbuilder |
| 全组合一个全局版本号 | 8 条接缝粒度不同，一个号要么过粗（改一处全升）要么过细（无法表达）；等价于没版本 |
| 不做版本化，靠 CI 全量回归兜 | 回归只能发现「今天这三仓能跑」，发现不了「明天某仓升级后形状变了」；且失败在**运行期** |
| 由各仓声明自己需要的契约版本（反向） | 变成「消费方定义生产方」，跨仓协商成本转移到每个仓，且无法防止两仓对同一契约要求冲突 |

## 后果（代价，不是收益）

1. **加契约是四步动作**：`protocols.py` 定义 → `CONTRACT_VERSIONS` 登记 →
   `CONTRACTS` 注册 → **在兄弟仓里**加 `SUPPORTED_CONTRACTS` 声明 → 补正例/负例测试。
   最后两步跨仓，需要在兄弟仓单独提 PR（本仓不吞并它们）。
2. **人工核对仍有残留风险，但比立项时小了**：2026-11-04 的 G6 在
   `tests/test_assembly.py` 补了三条机械断言，把「注册表版本 ↔ 三仓区间 /
   契约名 / 孤儿契约」固化（三仓缺失时明确 skip、CI 不 skip）。
   skip 不是通过：有 skip 时模块尾标记改为 `ALL_ASSEMBLY_TESTS_INCOMPLETE`
   且退出码 1，防止聚合 runner 的「退出码 0 + 尾标记」判据报假绿。
   **仍没有**「形状变了却忘了升版本」的机械门禁 —— `test_baseline.py`
   的快照锁契约名 / 版本号与「至少有一个方法」，**不锁方法名集合**。
   2026-11-05 变异体实测（真实 `check_provider`）分两组：**单边**加方法 /
   改方法名会被装配期响亮拒绝（`isinstance` 返回 `False`，见下方推论）；
   但**两类真空静默通过** —— ① 删方法 / 放宽协议（老提供方仍满足更弱协议），
   ② **协议与三仓 bridge 协同加方法却没升版本**（版本号仍在区间内、契约名未变，
   G6 三条联动断言与 `EXPECTED_CONTRACTS` 快照全 PASS）。真空 ② 恰恰是
   「契约版本与形状脱钩」、本 ADR 要防的核心情形，不能漏。
   这一半缺口见 [已知风险与缓解 §3](已知风险与缓解.md)。
3. **区间算术是自己实现的**：`_version.py` 只支持 `>= <= == != > <` 六个操作符
   与逗号分隔的区间串，不是 PEP 440 完整实现。够用，但别指望 `~=` / `*` 这类写法。
4. **契约号与组合仓自身版本号互不派生**：`superengine v0.2.0` 不表示任何契约是 2.0.0；
   契约全 1.0.0 时组合仓完全可能是 v0.9.0。两套计数器的区分见
   [`../release/版本策略.md`](../release/版本策略.md)。
5. **新增契约流程**已固化为可执行步骤，见
   [`../design/新增契约流程.md`](../design/新增契约流程.md)。
