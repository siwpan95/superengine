# 新增 / 变更契约流程（SOP）

> **适用**：往 `superengine` 加一条跨仓接缝，或改动既有接缝的**形状**。
> **不适用**：只改三仓内部实现、只改本仓装配层、只改 `worldspec v1` 文件格式（见 §0 第 4 门）。
> **前置阅读**：[契约矩阵速查.md](契约矩阵速查.md) · [契约体系设计.md](契约体系设计.md)（尤其 §6.3「有意不做」）。
> 契约层是零依赖的 `typing.Protocol`，改动会穿透四层文档，**别只改代码就收工**。

---

## 0. 先判「要不要」——四道否决门

按顺序问，任一门答「是」就**停**，不要往下走：

| 门 | 判定问题 | 若答「是」 |
|---:|---|---|
| 1 | 这条能力是否已被现有 8 个契约覆盖？（查 [矩阵速查 §1](契约矩阵速查.md)） | **复用现有契约**，需要的方法是既有形状的一部分就不要新建 |
| 2 | 是不是**某一个仓内部**自己的事（如 3dworld 内部的渲染契约）？ | **回那个仓**，别上提到组合仓。主设计 §6.3 明确这是纪律不是缺口 |
| 3 | 是不是想让两个兄弟仓直接 `import` 对方、绕过装配层？ | **拒绝**。违反 [ADR-002](../architecture/ADR-002-桥接层独占跨仓导入.md)，三仓必须可独立发布 |
| 4 | 是不是只想改 `worldspec` 落盘文件的字段？ | 那是**文件格式版本**，不是 `CONTRACT_VERSIONS`；见主设计 §2.4。别把两套号混了 |

> 通过四门仍要做，先写一句「这条接缝连接了谁和谁、走活对象还是文件」——
> 写不出来说明边界还没想清，回到 [契约体系设计.md §1.3](契约体系设计.md) 的三条干线定位。

## 1. 十步落地

每一步都给**文件**和**「怎么算做完」**；按顺序做，跳步会在第 8 步的基线测试里暴雷。

| 步 | 改哪个文件 | 做什么 | 怎么算做完 |
|---:|---|---|---|
| 1 | `superengine/contracts/protocols.py` | 加 `@runtime_checkable class Xxx(Protocol)`，**只含方法**、方法体 `...`；加进 `__all__` | `python -c "from superengine.contracts.protocols import Xxx; print(Xxx)"` 通过 |
| 2 | 同文件 `CONTRACTS` 字典 | 注册 `"snake_case_key": Xxx`，键名与第 3 步注册表键**逐字一致** | `CONTRACTS["xxx"] is Xxx` |
| 3 | `superengine/contracts/__init__.py` | import 新类、加进 `__all__`、`CONTRACT_VERSIONS` 加 `"xxx": "1.0.0"` | `python selfcheck.py` 仍全绿（注册表一致性检查会覆盖新键） |
| 4 | **提供方仓**的 `bridge.py` | 实现方法 + `SUPPORTED_CONTRACTS` 加 `"xxx": ">=1.0,<2.0"` | 该仓自己的测试全绿。**跨仓改动走单独 PR**，不混进本仓提交（ADR-002） |
| 5 | `superengine/bridges/<repo>_bridge.py` | 把能力挂成 Service 的方法（**唯一允许 import 三仓的地方**） | 单独 `python -c "import superengine.bridges.<repo>_bridge"` 不抛异常 |
| 6 | `configs/cordis.super.yml` | 若需新 entry，`name` 必须以 `superengine.bridges.` 开头（白名单），并写清 `inject` | `boot --report` 打印的 fiber 里新服务是 `ACTIVE` |
| 7 | `tests/test_assembly.py` / `test_pipeline.py` / `test_no_cross_import.py` | 结构断言、端到端、边界扫描各补一条 | 三个模块各自的 `ALL_*_TESTS_PASSED` 仍出现 |
| 8 | `tests/test_baseline.py` 的 `EXPECTED_CONTRACTS` | **加新条目**（这是最常漏的一步） | `python -m tests.test_baseline` → `ALL_BASELINE_TESTS_PASSED`（当前 9 项断言）；同时 `test_assembly.py` 的 G6「孤儿契约」断言会因新契约尚无提供方而变红，直到第 4 步完成 |
| 9 | 四层文档（见 §4） | 回写，别只改代码 | 所有 `docs/...` 引用可点开 |
| 10 | 全量门禁（见 §3） | 逐条实跑并记录 | `ALL_TESTS_PASSED` + `SUPERENGINE_BOOT_OK` + `SUPERENGINE_DEV_OK` |

> **第 5 步的红线**：`bridges/` 之外出现任何 `import worldbuilder` / `world3d` / `allin_engine`
> 都会被 `tests/test_no_cross_import.py` 拦下。契约层（`contracts/`）连第三方依赖都不能有，
> 由 `test_baseline.py::test_contracts_layer_is_dependency_free` 守着。

## 2. 版本号怎么 bump

> **唯一事实源声明（判据单一事实源方案 B，已落地）**：契约号 **bump 判据的本体**在
> [`../release/版本策略.md`](../release/版本策略.md) §3（`§3.1` 判据表、
> `§3.2` 加方法即破坏的实测、`§3.3` 区间语义、`§6` 什么时候动契约号）。
> 本节是**流程侧的索引**，只写「做这一步时该去查什么、查完要动哪些文件」，
> 不复述判据、不另立一套规则 —— **一条规则不写第二遍**。
> 主设计 [契约体系设计.md](契约体系设计.md) §5 / §7.2 则负责**为什么**这样定
> （独立性推演、`isinstance` 只查方法存在性），三者分工不重叠。
> ⚠️ 这里的「方案 B」**不是**本文件末尾那个待裁的 **#11 A/B（方法名快照）**，见 §2 末的消歧块。

`CONTRACT_VERSIONS` 与 `pyproject.toml` 的 `version` 是**两套独立计数器**
（[版本策略](../release/版本策略.md) §1）。查完 §3 后，本节要落实的动作：

| 你做的事 | 契约号动作 | 同步要改的 | 依据 |
|---|---|---|---|
| **新加一条契约**（既有 8 条不动） | 新契约从 `1.0.0` 起；既有**全不动** | 三仓中提供方仓的 `SUPPORTED_CONTRACTS` 加 `"xxx": ">=1.0,<2.0"` | 版本策略 §3.1 minor / 主设计 §5 |
| **给已有契约加 / 删 / 改方法** | 该契约 **major**（`1.0.0 → 2.0.0`） | **三仓全部** `SUPPORTED_CONTRACTS` 区间同步到 `>=2.0,<3.0`；组合仓版本一并动 | 版本策略 §3.2 实测 / 主设计 §7.2 风险 2 |
| 只改注释 / 文档 / 测试 | 不动 | 无 | 形状没变 |
| 兄弟仓自己发版 | **不动** | 无 | 契约号不跟随任何一仓（主设计 §5） |

**这是两条不同的路，别混**（release-ops-lead 在 SE-C 收结里特别点出）：

- **新增契约** = 新的 `Protocol` → 老提供方一行都不用改 → 契约 **minor**（新契约自己的 `1.0.0`）。
- **扩展已有契约** = 往老 `Protocol` 里塞方法 → 契约 **major**，
  且**必须通知三仓**更新区间与实现。「加个可选方法算 minor」的直觉在本仓是错的，
  因为 `check_provider` 走的是裸 `isinstance`，没有「可选方法」这回事。
  ⚠️ 「老提供方在装配期直接失败」**只在单边改动时成立**：若三仓 bridge 已同步实现
  新方法，`isinstance` 反而通过（见下方真空 ②）——**形状变了就是变了，
  不因「这次装得上」而免掉 major bump**。

历史上 `dungeon_source` / `rules_kernel` 就是走第一条路（`6cfcbea` 作为两个
**新契约**加入，而不是往已有契约里塞方法）—— 现在看是对的。

改 major 时若**只升 `CONTRACT_VERSIONS` 而忘了三仓区间**，装配期 `check_all`
会以「版本不在区间」拒掉 —— 这正是门禁想要的行为，**别去放宽区间绕它**。

**判据要显式覆盖真空 ②**（engineering-lead / quality-lead 实测）：
形状变了 —— 无论**单边还是协同**、**加 / 删 / 改** —— 只要没同步升
`CONTRACT_VERSIONS`，就必须人工确认并同步该契约号与**三仓**
`SUPPORTED_CONTRACTS`。判断依据**不是「装配有没有报错」**：
协同改动（`Protocol` 与三仓 bridge 一起加方法、版本号没动）下
`1.0.0` 仍落在 `>=1.0,<2.0`、`EXPECTED_CONTRACTS` 未变 ⇒
**全仓门禁静默通过**，这是最容易被「测试全绿」骗过去的一种。
⇒ 第 1~7 步做完**不等于**契约已升级，第 3 步的 bump 是硬性收尾动作。

> **判定「形状变了没」目前没有机械断言兜底**（诚实边界）：
> `tests/test_baseline.py::test_protocol_methods_are_declared` 只
> `assert methods`，即**断言「每个契约至少声明了一个方法」**，
> **并不**把方法名集合固化成快照；`EXPECTED_CONTRACTS` 锁的是
> **契约名 → 版本号**，也不锁方法签名。整体 `tests/` 无 `EXPECTED_METHODS` 常量。
> ⇒ 「**形状变了却忘了升版本号**」这件事，**当前没有任何机械门禁（断言或装配期检查）会响**；
> 其中 `test_baseline.py` 尤其不会因为方法名/签名变化而变红。
> 只能按 §1 的人工步骤 + code review 判定，并用 [版本策略 §3.2](../release/版本策略.md)
> 的实测结论做判据依据。
>
> 上半句的「没有断言会红」是**特指方法名/签名没有被固化成快照**。装配期另有
> 一层 `check_provider`，但它是**满足性检查**（当前提供方是否满足当前 Protocol），
> **不是差异检查**，所以只对单边改动有效、对协同改动无效 —— 这也正是真空 ② 的根因
> （主设计 §4.3 有同款论证）。
> 2026-11-05 变异体实测因此把残留面界定为**两类真空**（见
> [`ADR-001`](../architecture/ADR-001-契约独立版本化.md) 后果 2 与
> [`已知风险与缓解 §3`](../architecture/已知风险与缓解.md)）：
>
> | 场景 | `check_provider` | 结论 |
> |---|---|---|
> | **单边**：只改 Protocol（加方法 / 改名），老提供方不动 | **REJECTED** | 装配期响亮拒绝，拦得住 |
> | **删方法 / 放宽协议** | **ACCEPTED（静默）** | **真空 ①** |
> | **协同**：Protocol 与三仓 bridge 同步加方法，忘升 `CONTRACT_VERSIONS` | **ACCEPTED（静默）** | **真空 ②**：版本仍在区间内、契约名未变 ⇒ G6 与 `EXPECTED_CONTRACTS` 全 PASS，**全仓无断言会红** |
>
> ⇒ 「加方法 / 改名会被拦」只在**单边**成立，且拦它的是**装配期 `ContractVersionError`**，
> **不是任何测试断言变红**；协同改动下两类门禁都不响。
> 别写成「形状变更完全无人把关」，也别写成「改方法就有断言会红」——
> 两个方向都不准确。**真空 ② 是本 SOP 最该防的**：
> 三仓实现全跟上了、测试全绿，唯独版本号没动 —— 下游按旧契约编译的调用方
> 仍可能在运行期炸。**跨仓同步实现新方法 ≠ 契约已升级**：
> 第 1~7 步做完后，**必须回来做第 3 步的 major bump 并同步三仓 `SUPPORTED_CONTRACTS`**。
>
> ⚠️ **消歧（两个「B」不是一回事）**：本段的 **#11 A/B（方法名快照）** 仍**待主理人裁定**；
> 而本文 §2 开头「**判据单一事实源方案 B**」是**已落地**的另一件事
> （bump 判据本体留 [`版本策略.md`](../release/版本策略.md) §3、设计层压成索引）。
> 别把「判据单一事实源已选 B」误读成「方法名快照已决定补」。发布面
> [`版本策略.md §3.2`](../release/版本策略.md) 有同一条消歧块，两头可对照。
>
> **#11 A/B（方法名快照）**：是否补一条机械门禁，本文不预设立场。
> 两种裁定结果对应的回写动作：
> - 选 **A**（只纠文档）：本节维持「无机械门禁，靠人工步骤 + code review」；
> - 选 **B**（补 `EXPECTED_METHODS` 快照）：落地后回来把本节改成
>   「**两类真空都不再静默**（方法名集合变了 ⇒ 快照红，逼出显式确认）」。
>   但**粒度必须守住**：快照与 `CONTRACT_VERSIONS` **无派生关系**，
>   它**不**机械强制「加方法按 major 升版本」——那一半仍是本 SOP 的人工纪律 + code review。
>   措辞用「形状变更不再静默」，**禁写**「升级已自动化 / 已闭环」。

## 3. 落地后的门禁清单

在本仓 `.venv`（含 `pyglet`）里逐条跑，全部要绿：

```bash
python selfcheck.py                          # 契约层无头自检（当前 23 checks）
python -m tests.run_tests                    # 8 模块 / ALL_TESTS_PASSED
python -m superengine.cli.boot --report      # 末行 SUPERENGINE_BOOT_OK，fiber 全 ACTIVE
python -m superengine.cli.dev --once         # 末行 SUPERENGINE_DEV_OK
python scripts/bootstrap.py --check-only     # 干净机依赖声明自检
```

CI 侧还要过三平台（Windows / Linux headless / macOS）矩阵，见
[`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) 与 [门禁标准](../quality/门禁标准.md)。
**本机只证 Windows**；Linux/macOS 的 pyglet 懒加载结论要由对应 runner 自证，
别把本机实测直接当成三平台结论。

## 5. 一个反例：跳过第 8 步会怎样

`test_baseline.py` 把 `CONTRACT_VERSIONS` 固化成 `EXPECTED_CONTRACTS` 快照。
若只做了第 1~7 步就提交：

- 本机 `tests.run_tests` 会红在 `test_baseline::test_contract_registry_snapshot`；
- 有人为了「让测试变绿」直接放宽快照 ⇒ 基线失守，
  下次有人偷偷改契约号就没人拦得住 —— 这正是 2026-11-04 `pyglet` 事故的同型失效
  （长期把真实问题当环境问题绕过去，见 [回归基线](../quality/回归基线.md)）。

**正确做法**：把快照更新当成「我确认过这次变更是有意的」这一动作本身，随 PR 一起评审。
