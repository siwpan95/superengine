# 契约体系设计 —— superengine 的跨仓接缝是怎么定义的

> **这份文档回答什么**：本仓（组合仓）只做四件事——**契约、桥接、装配、门禁**，不含任何算法。
> 三仓（`worldbuilder` / `an-engine` / `3dworld`）各自独立发版、互不引用，
> 却仍然能协作——**唯一的纽带就是这一层契约**。
>
> **这份文档不回答什么**：它不描述三仓内部怎么实现算法，也不规定业务玩法。
> 契约层只管**形状**（方法签名与语义），不管**内容**。
>
> **核对日期**：2026-11-04。全部结论来自对本仓与三仓源码的实测，文中标注
> 「实测」处附了可复现的判据。与版本号/bump 判据相关的部分，与
> [`../release/版本策略.md`](../release/版本策略.md) 保持一致（该文管**什么时候动号**，
> 本文管**为什么这样设计**）。

---

## 0. 一句话定位

**契约层是「三仓互不引用却仍能协作」的底线。**

这句话每个字都是实的，展开说：

| 半句 | 对应机制 | 在哪 |
|---|---|---|
| 三仓互不引用 | 静态 + 运行时双重扫描门禁 | `tests/test_no_cross_import.py` |
| 仍能协作 | 8 个跨仓接缝的**形状约定** | `superengine/contracts/protocols.py` |
| 底线 | 形状漂移在**装配期**炸，不留到运行期 | `superengine/contracts/__init__.py` 的 `check_provider` |

为什么必须是「底线」而不是「便利」：三仓独立发版是**不可协商的前提**
（兄弟仓有自己的用户、自己的 CHANGELOG、自己的发版节奏）。
一旦三仓互相 import，就从「可独立发布」退化成「一损俱损」，而且
**编译期不会报错**——这是整合最容易死的地方，也是本仓第一道扫描门禁存在的理由。

## 1. 8 个契约的职责边界与相互关系

### 1.1 全景：谁生产、谁消费、数据怎么流

```
                       ┌──────────────────── worldbuilder ────────────────────┐
                       │  纯 numpy · 无 GL · 无第三方依赖                       │
                       │                                                        │
   文件契约(worldspec)  │  generate ──► height/biome/water/...                 │
   ─────────────────►  │  generate_complete ──► + pois/roads(=graph)          │
   （落盘 · 跨进程）     │  generate_dungeon ──► grid/rooms ──► dungeon_graph    │
                       │  grammar_names                                        │
                       └───────────────┬───────────────┬────────────────────────┘
                                       │               │
              ① terrain_source        │               │ ② worldspec_source
                 heightfield           │               │    generate/save/load/validate/meta
                 make_height_sampler   │               │
                                       ▼               ▼
                       ┌──────────────── worldbuilder bridge ─────────────────┐
                       │        （唯一 import 三仓的地方）                      │
                       └───────┬───────────────────────┬──────────────────────┘
                               │                       │
              ┌────────────────┘                       └────────────────┐
              │  (f(x,z)->h) 同进程不落盘                            │  spec_dir
              │                                                     │  （graph.json / pois.json）
              ▼                                                     ▼
   ┌────────────────────────┐                    ┌────────────────────────────┐
   │        3dworld          │                    │          an-engine          │
   │  ③ terrain_sink         │                    │  ④ mapgraph_source         │
   │     clipmap_config      │                    │     mapgraph_from_worldspec │
   │     terrain_mesh        │                    │     route / nearest         │
   │  ⑤ render_sink          │                    │  ⑥ gameplay_world           │
   │     terrain_from_heightfield │               │     new_context             │
   └────────────────────────┘                    │     provide_mapgraph        │
              ▲                                   │  ⑦ rules_kernel             │
              │                                   │     roll_dice/roll_d20/...  │
              │  ⑧ worldspec_source（反向读盘）      └────────────────────────────┘
              └──────────────────────────────────────────┘
```

### 1.2 逐条职责边界

| # | 契约 | 提供方 | 消费方 | 关键方法 | 边界（**不**管什么） |
|---|---|---|---|---|---|
| 1 | `worldspec_source` | worldbuilder | 本仓装配层 + 外部集成者 | `generate` / `save` / `load` / `validate_spec` / `meta` | 不管世界的**内容**（地形算法、群系规则） |
| 2 | `terrain_source` | worldbuilder | 3dworld（经本仓桥接） | `heightfield` / `make_height_sampler` | 不管**坐标解释权**——由产出方定义（见 §3.2） |
| 3 | `dungeon_source` | worldbuilder | *（目前无仓内生产消费方，见 §6.1）* | `generate_dungeon` / `dungeon_graph` / `grammar_names` | 不管关卡**可解性**的玩法语义（锁/钥匙的规则） |
| 4 | `mapgraph_source` | an-engine | 玩法侧 | `mapgraph_from_worldspec` / `route` / `nearest` | 不管图**从哪来**（worldspec 目录 or 地牢图） |
| 5 | `gameplay_world` | an-engine | 本仓（托管玩法世界） | `new_context` / `provide_mapgraph` | 不管玩法**状态机**（战斗、库存、任务） |
| 6 | `rules_kernel` | an-engine | 玩法侧 | `roll_dice` / `roll_d20` / `roll_3d6` / `success_chance` | 不管**规则内容**（数值出自 SRD 5.1，见 §3.3） |
| 7 | `terrain_sink` | 3dworld | 本仓 + 表现层 | `clipmap_config` / `terrain_mesh` | 不管**网格算法**（clipmap 细节是 3dworld 内部） |
| 8 | `render_sink` | 3dworld | 表现层（备用路径） | `terrain_from_heightfield` | 不管**渲染**（本仓全程 headless / 零 GL） |

### 1.3 数据流的三条独立干线

契约不是一张网，是**三条互不干扰的干线**。把它们的边界分清，才知道出事时该查哪条。

| 干线 | 链条 | 载体 | 特点 |
|---|---|---|---|
| **地形干线** | worldbuilder → 3dworld | **活对象**（`f(x,z)->h` 采样器） | 同进程、不落盘、零序列化成本 |
| **玩法干线** | worldspec 目录 → an-engine | **文件**（`graph.json` / `pois.json`） | 跨进程可读、历史快照可复现 |
| **规则干线** | 调用 → an-engine | **数值**（骰子） | 无状态、纯函数式 |

> 三条干线用**两种传递方式**（活对象 / 文件），这直接决定了 §2 那条正交轴的存在。

## 2. 两条正交轴：文件契约 ↔ 服务契约

这是理解本仓设计的钥匙。它是一条**正交轴**——两个方向互不替代、可以并存。

### 2.1 两条轴各自的定义

| | **文件契约** | **服务契约** |
|---|---|---|
| 代表 | `worldspec v1` | cordis 的 8 个 `@runtime_checkable` Protocol |
| 载体 | 一个目录（`meta.json` + `.npy` + `.json`） | 进程内的**活对象** |
| 版本载体 | 数据**自描述**：`meta["spec"] == "worldspec/1"` | 中央注册表：`CONTRACT_VERSIONS` |
| 版本裁决 | **严格等值**，不匹配直接拒读 | **兼容区间**算术，落在区间外即报错 |
| 谁裁决兼容 | **读者**（消费方自己比对 `spec` 串） | **装配器**（`check_provider` 在装配期裁决） |
| 生命周期 | 独立于进程；可复制、可归档、可发给别人 | 与进程同生共死；可挂载/卸载/回滚 |
| 装配器做什么 | **不参与**（文件契约走的是普通函数调用） | 校验版本 + 结构（`isinstance`） |

### 2.2 「什么时候用哪条」的判据

不写套话，直接给可执行的判据。**按顺序问三个问题，第一个「是」就定了：**

**判据 1（最关键）：消费方需要的是「活对象」还是「耐久值」？**

- 需要**活对象**（要调方法、要生命周期、要能随装配层一起回滚）
  ⇒ **服务契约**。
  例：`terrain_mesh(height_fn, ...)` 要的是那个函数；`new_context()` 要的是那个可 `provide`/`dispose` 的容器。

- 需要**耐久值**（要存盘、要跨进程、要给第三方、要归档复现）
  ⇒ **文件契约**。
  例：`mapgraph_from_worldspec(spec_dir)` 要的是磁盘上那个目录。

**判据 2：数据要跨越的边界里，有没有「时间」或「机器」？**

- 跨越**时间**（生产与消费不在同一刻）或**机器**（不同进程/不同机器）
  ⇒ **文件契约**。worldspec 的全部意义就在这一条。

- 只跨越**函数调用**（同进程、同一次调用栈内）
  ⇒ **服务契约**更划算：落盘再读回来是纯浪费。

**判据 3：双方是否必须同时在场？**

- 必须同时在场（一方下线，另一方就没意义了）
  ⇒ **服务契约**（cordis 的 `inject` 依赖图正是为此存在）。

- 不必同时在场（三个月前产出的世界，今天的新版 an-engine 仍要能读）
  ⇒ **文件契约**。

### 2.3 为什么两条并存、且**不互相替代**

> 「worldspec 正是『三仓互不引用却仍能协作』的底线」——这句写在 README 纪律 3 里，
> 不是修辞，是**唯一能让三仓互不引用还协作的机制**。

**文件契约不能替代服务契约**，因为：

1. **文件契约没有生命周期语义。** 服务契约经由 cordis 的 fiber 管理，
   消费方卸载时提供方随之回滚（M3 热重载靠的就是这个：旧 fiber 完整回滚、
   新 fiber 换入，判据是 registry 规模不增长）。文件契约是一堆躺在盘上的字节，
   没有「卸载」这回事。
2. **文件契约每次都要付序列化成本。** 地形干线每帧要的是采样器；
   把它落成 `.npy` 再读回来，是纯粹的浪费。
3. **文件契约没有装配期门禁。** `worldspec/1` 的兼容性由**读者**在**运行期**比对
   `meta["spec"]` 才发现；服务契约的兼容性由**装配器**在**装配期**裁决。
   这两者的时间差，就是「装配期炸 vs 运行期炸」的区别。

**服务契约不能替代文件契约**，因为：

1. **服务契约要求双方同时在场。** worldbuilder 发了新版、an-engine 还在用旧版
   （或进程根本没起）——这时只有文件契约能让两个**独立发版**的仓对上话。
2. **文件契约自带版本戳与元信息。** `meta.json` 记着 `spec` / `generator` / `seed` /
   `size` / `tile_m` / 坐标约定（右手系、Y 上、r→+z、c→+x）。
   这让「这份数据是哪来的、怎么解释」**自包含**，不依赖任何一方的当前代码状态。
3. **文件契约可以被非 Python 消费者读。** 服务契约是 Python `Protocol`，
   换语言就断了；`graph.json` 是 JSON，谁都能读。

**现状：两条都真在跑，不是纸面设计。**

- 服务路径：`tdworld_bridge.terrain_from_world()` —— 同进程、不落盘
  （`tests/test_pipeline.py::test_m1_worldbuilder_to_3dworld_terrain` 断言）。
- 文件路径：`worldbuilder.save()` → 目录 → `anengine.mapgraph_from_worldspec()`
  （`test_m1_worldspec_roundtrip` 断言高程**逐位**一致）。

### 2.4 一个容易搞混的点：**契约版本 ≠ 文件格式版本**

这是两套完全独立的号，别混：

| | 文件格式版本 | 契约版本 |
|---|---|---|
| 位置 | `meta.json` 的 `spec` 字段 | `CONTRACT_VERSIONS` |
| 值 | `"worldspec/1"` | `"1.0.0"` |
| 粒度 | 整个 worldspec 格式一套 | **每个契约一个** |
| 裁决 | 严格等值，不匹配拒读 | 区间算术 |
| 谁能改 | worldbuilder（格式的产出方） | 本仓（组合仓），**独立于任何一仓** |

`worldspec/1` 升到 `worldspec/2` 时，`worldspec_source` 契约**不必**动版本号——
除非 `generate`/`save`/`load` 的**签名**变了。反过来契约升到 `2.0.0`，
`worldspec/1` 格式可能纹丝不动（只是接缝方法变了）。

## 3. 三个关键机制的设计理由

### 3.1 同形复用：`dungeon_graph` ↔ `graph.json`

> 这是本仓最精巧的一处设计，也是**最容易被过度解读**的一处。必须把「安全在哪」
> 和「边界在哪」都讲清楚。

#### 3.1.1 它是什么

`dungeon_source.dungeon_graph(grid, locks=, loops=, seed=)` 产出一个 dict，
其 `nodes` / `edges` 的**字段词汇**与 worldspec 落盘出来的 `graph.json` 一致：

| `graph.json`（路网） | `dungeon_graph`（地牢） | 字段含义 |
|---|---|---|
| `nodes[].id` | `nodes[].id` | 节点唯一标识 |
| `nodes[].kind` | `nodes[].kind` | 节点类型（`town`/`entrance`/`boss`/…） |
| `nodes[].x` / `.z` | `nodes[].x` / `.z` | 格坐标 |
| `nodes[].name` / `.score` | `nodes[].name` / `.score` | 名字 / 权重 |
| `nodes[].meta` | `nodes[].meta` | 附加信息 |
| `edges[].a` / `.b` | `edges[].a` / `.b` | 两端节点 id |
| `edges[].kind` / `.length` / `.cost` / `.points` | 同名 | 边类型 / 长度 / 代价 / 折线 |

所以 an-engine 的 `MapGraph` **能直接吃它**——生成 → 玩法共用一套形状。

#### 3.1.2 为什么这个复用是**安全**的

四条理由，每条都有实测支撑：

1. **它复用的是「数据形状」，不是「代码」**。两边的节点/边都是
   **纯 dict / list / 标量**，没有对象身份、没有类绑定、没有回调。
   契约层禁止 import 三仓，所以形状一致是**唯一**可能的耦合方式——
   这恰恰是「三仓互不引用」纪律下**唯一还能耦合的地方**。

2. **消费方对未知字段是宽容的，对缺失字段有默认值**。
   `MapGraph.from_worldspec` 用 `row.get("x", 0.0)` / `e.get("length")` 这类读法，
   多出来的字段被忽略、少掉的字段退到默认值。**实测**：
   把 `dungeon_graph` 的产物写成 `graph.json` 后，`from_worldspec(..., strict=True)`
   正常读出 5 节点 / 4 边，`route()` 能算出路径。

3. **它省掉的是一段真实的重复劳动**。没有同形复用，worldbuilder 就得为
   地牢单独产一套 an-engine 认的格式，an-engine 就得多写一个解析器。
   同形复用让「地牢」和「路网」这两类完全不同的世界内容，
   **共用同一条下游管线**。

4. **它不违反任何一条纪律**。三仓仍然互不 import；同形只是**数据层**的巧合，
   而这个巧合被 `worldspec/1` 的 `spec` 串钉死（谁改了字段，
   `spec` 串就会变，旧读者拒读）。

#### 3.1.3 边界在哪——**实测出来的，不是推测**

同形复用的边界比注释里写的「同形」**窄**。以下全部是实测结果：

| 语义 | 走 `dungeon_graph` 直取 | 经 `worldspec.save()` → `graph.json` | 经 `MapGraph.from_worldspec()` |
|---|---|---|---|
| `nodes` / `edges` 的**字段词汇** | ✅ | ✅ | ✅ |
| 顶层 `keys`（钥匙清单） | ✅ 有 | ❌ **丢**（`graph.json` 只有 `nodes`/`edges`/`spec`） | ❌ 无处安放 |
| 顶层 `entrance` / `boss` | ✅ 有 | ❌ **丢** | ❌ |
| 顶层 `stats` | ✅ 有 | ❌ **丢** | ❌ |
| `edges[].key`（哪把钥匙开哪扇门） | ✅ 有 | ❌ **丢**（`save()` 只写 a/b/kind/length/straight/cost/points） | ❌ |
| `nodes[].meta.bbox/area/depth/tags` | ✅ 有 | ✅ 保留在 `nodes[].meta` | ⚠️ **只剩** `x/z/kind/tile_m/score`（+ `elevation`/`biome`/`slope`） |
| `edges[].straight` | ✅ 有 | ✅ 保留 | ❌ 不进 `MapGraph` 的边信息 |

**结论**：`dungeon_graph` 与 `graph.json` 同形的，是**图拓扑的字段词汇**；
**地牢专属的语义**（钥匙、上锁边的钥匙绑定、入口/Boss 标记、统计）
**不在同形范围内**，经文件路径会被丢弃。

> 这不是 bug，是「同形」的固有代价：`graph.json` 是**路网**格式，
> 它没有「钥匙」这个概念。复用拓扑、丢弃语义，是这种复用的**必然代价**。
>
> **推论（重要）**：任何需要「钥匙 ↔ 锁边」绑定的玩法，
> **不能靠 `graph.json` 这条路**——必须直接吃 `dungeon_graph()` 的原产物。
> 这一点当前**没有写进任何契约或文档**，是本设计文档要补上的认知。

#### 3.1.4 还有一条**没被复用**的路（诚实边界）

`MapGraph` 有两个构造入口，形状**不一样**：

| 入口 | 期望 `nodes` 形状 | 能吃 `dungeon_graph` 产物吗 |
|---|---|---|
| `MapGraph.from_worldspec(spec_dir)` | **list**（`graph.json` 形状） | ✅ 经文件后可以 |
| `MapGraph.from_dict(data)` | **dict**（`MapGraph` 自己的嵌套序列化形状） | ❌ **不能** |

**实测**：`MapGraph.from_dict(dungeon_graph)` 直接抛
`AttributeError: 'list' object has no attribute 'items'`。

所以「同形复用」当前**只在文件路径上兑现**：
`dungeon_graph` → 写盘 → `from_worldspec`。**内存直传没有通路。**
若将来需要「地牢图零落盘直接喂给玩法」，需要新增一个显式的适配入口
（这属于新增契约的范畴，见 [`新增契约流程.md`](新增契约流程.md)）。

### 3.2 坐标解释权归**产出方**

`terrain_source.make_height_sampler(hm, tile_m=, height_scale=)` 产出一个
`f(world_x, world_z) -> height` 的采样器；`terrain_sink.terrain_mesh(height_fn, ...)`
消费它。

**为什么坐标解释权必须在产出方（worldbuilder）手里？**

因为**高程阵列的行主序与坐标系绑定在生成侧**：`height[r][c]` 的 `r → +z`、
`c → +x`，右手系、Y 上。表现层若自己解释，就等于**复制一份坐标约定**——
两份约定迟早漂移，而漂移的表现是「地形整体旋转/镜像了」，极难排查。

所以本仓的纪律是：**表现层只消费 `f(x, z) -> h`，不碰数组语义。**
实测判据见 `tests/test_pipeline.py::test_m1_sampler_matches_heightfield`：
整数格点处采样值必须**回到格值本身**（`tile_m=2` ⇒ 世界 10m → 第 5 列），
`r→+z`、`c→+x`、`tile_m` 归产出方解释，三者同时成立。

### 3.3 规则内核与许可边界

`rules_kernel` 只暴露骰系（`roll_dice` / `roll_d20` / `roll_3d6` / `success_chance`）。
数值来源是 an-engine 自带的 **SRD 5.1 / CC-BY-4.0** 数据条款，
分发时随仓携带 `NOTICE`（见 README 许可节）。

**为什么契约层要显式写这件事**：`rules_kernel` 是唯一一个**数值内容有外部许可约束**
的契约。别人写代码时若照抄这份数值而不带 `NOTICE`，就是许可违规。
把这条写进契约 docstring，是让**每个经手这条接缝的人**都看得见。

> 对照：`protocols.py` 的模块 docstring 明确写了
> 「**上提而非新建**」——`render`/`terrain`/`entity` 等能力 3dworld 已有自己的契约
> （`world3d.core.contracts`，**15 个** Protocol），本模块只定义**跨仓**接缝，
> 表现层内部契约仍由 3dworld 自己管，**避免两套契约漂移**。
> 这条纪律直接决定了 §6 的缺口判断——**别把「3dworld 内部已有」误报成「本仓缺」**。

## 4. 契约版本与兼容区间机制

### 4.1 为什么**主版本不同即视为不兼容**

语义化三段号 `MAJOR.MINOR.PATCH`，其中 MAJOR 的含义是
「**老提供方按老接口实现就装不上了**」。

为什么 MAJOR 一定要这么严格？因为接缝的消费者是**写死在别人代码里的调用点**。
契约降级成「试试看能不能用」的那一天，就再也无法回答
「我升级了之后到底还能不能连」这个问题了。而这个问题的答案必须是**可判定的**。

**主版本不同即不兼容**，把「可判定」落在了区间算术上：
契约版本必须落在提供方声明的区间内，否则装配期抛 `ContractVersionError`。

> **一个必须说清的精确性**（实测）：「主版本不同即不兼容」在实现上是
> **区间串的书写约定**，**不是算术强制**。
> `>=1.0,<2.0` 会排除 `2.0.0`；但若有人只写 `>=1.0`（无上界），
> **实测 `2.0.0` 依然匹配**。也就是说：**没有代码在强制「主版本不同即不兼容」，
> 是「大家都这么写」这个约定在保证它。**
> 这是新增契约时必须守住的一条（见 [`新增契约流程.md`](新增契约流程.md) 第 4 步）。

### 4.2 区间串的写法与语义

`parse_interval` 把区间串切成 `(运算符, 版本元组)` 列表，**逐条 AND**。

| 写法 | 解析结果 | 语义 | 典型用途 |
|---|---|---|---|
| `">=1.0,<2.0"` | `[('>=',(1,0,0)), ('<',(2,0,0))]` | `1.0.0 ≤ v < 2.0.0` | **最常用**：任何 1.x 都行 |
| `"==1.2.0"` | `[('==',(1,2,0))]` | 精确等于 | 钉死单点（极少用：太脆） |
| `">=1.1"` | `[('>=',(1,1,0))]` | 无上界 | ⚠️ **慎用**：实测会匹配 `2.0.0` |
| `"1.2.0"`（裸版本） | `[('==',(1,2,0))]` | 等价于 `==1.2.0` | 简写 |
| `">=1.0,<2.0,!=1.3.0"` | 三条 AND | 区间内再排除一点 | 极少用 |

支持的运算符：`>=` `<=` `==` `!=` `>` `<`。版本元组缺位补 0（`1.2` → `(1,2,0)`）。
区间串解析不了（`"banana"`）或为空（`""`）⇒ 抛 `ContractVersionError`。

**三仓当前的声明（实测自各仓 `bridge.py`）**：

| 仓 | `SUPPORTED_CONTRACTS` |
|---|---|
| worldbuilder | `worldspec_source` / `terrain_source` / `dungeon_source` → 全部 `">=1.0,<2.0"` |
| an-engine | `gameplay_world` / `mapgraph_source` / `rules_kernel` → 全部 `">=1.0,<2.0"` |
| 3dworld | `terrain_sink` / `render_sink` → 全部 `">=1.0,<2.0"` |

### 4.3 `check_all` 的**方向性**——为什么不能反过来要求

```python
def check_all(versions, supported):
    for name in supported:          # ← 遍历「该仓声明自己有什么」
        if name not in versions:
            raise ContractVersionError(f"该仓声明了未知契约 {name!r}...")
        check_compat(name, versions[name], supported)
```

- `supported` = 「该仓能提供什么」
- `versions` = 「契约现在是什么版本」

**遍历的是 `supported`，不是 `versions`。** 方向不能反过来，因为
**三仓的能力是不对称的、而且永远不对称**：worldbuilder 不会提供 `terrain_sink`，
3dworld 不会提供 `mapgraph_source`。若反过来要求（每仓都得满足全部 8 条），
这个模型就塌缩成「一个大仓」，而「三仓平等、互不吞并」正是本仓存在的理由。

**两个方向的后果（实测）**：

| 情形 | 结果 |
|---|---|
| 某仓声明了注册表里没有的契约 | ✅ **报错**（`该仓声明了未知契约 'bogus'`）——挡住拼写错误 |
| 某仓**没有**声明某条契约 | ⚠️ **不报错**——`check_all` 只查它声明的那些 |
| 某契约**没有任何仓提供** | ⚠️ **不报错**——实测：把 worldbuilder 的 `dungeon_source` 声明撤掉，`check_all` 照样返回 `None` |

**最后一条是当前门禁的一个真实盲区**，值得记下来：
「契约无人提供」这件事**没有任何机制会发现**。
现状 8 条契约**全部**有提供方（实测覆盖检查：8/8），但这靠的是人工保持，
不是机器保证。新增契约时若三仓都还没接上，机器不会提醒——
只能靠新增契约流程里那条「**声明了就要真接上**」的人工检查项兜住。

> **顺带澄清一处文档与实现的措辞差异**（诚实边界）：
> `check_compat` 的 docstring 说「契约未被声明同样报错」——这在
> **单点调用** `check_compat(contract, ...)` 时成立（点名问某契约而该仓没声明 ⇒ 报错）。
> 但 `check_provider` 走的是 `check_all`，**不会**因为「该仓没声明某契约」而报错。
> 两个函数的语义粒度不同，不是 bug，但容易读岔。

## 5. 契约的**独立性**论证

### 5.1 结论先行

**契约版本必须独立于三仓发版节奏。**这不是风格偏好，是**功能性必需**——
一旦契约号跟随某一仓，另外两仓就被那一仓的节奏绑架。

### 5.2 失效场景推演（假设契约号跟随 worldbuilder）

worldbuilder 发了个 v2.0.0，把 `generate` 改名为 `generate_world`。

| 步骤 | 若契约号跟随 worldbuilder | 实际后果 |
|---|---|---|
| 1 | `worldspec_source` 契约版本 → `2.0.0` | —— |
| 2 | an-engine 声明 `mapgraph_source: ">=1.0,<2.0"` | an-engine **完全没碰** `mapgraph_source`，却因**另一个仓的破坏性改动**被连坐 |
| 3 | 装配期 `check_provider` | 抛 `契约 'mapgraph_source' 版本 2.0.0 不在该仓声明的兼容区间` |
| 4 | 读者看到这条报错 | **完全看不懂** —— mapgraph_source 的形状根本没变 |

于是会立刻出现两个坏选择：

- **坏选择 A**：把 an-engine 的声明放宽成 `>=1.0,<3.0` —— 于是
  **所有**契约的区间都被稀释成「基本什么都能过」，区间校验退化成摆设。
- **坏选择 B**：每次 worldbuilder 发版都要去三仓改一遍 `SUPPORTED_CONTRACTS` ——
  契约层从「自动裁决」退化成「人工同步」，而人工同步必然漏。

**还有更隐蔽的一种**：worldbuilder 修个 bug 发 v1.0.2，
契约号跟着变成 `1.0.2`，**所有三仓**用 `==1.0.0` 那种精确声明的直接全炸。
—— 一个与契约形状毫无关系的修复，凭什么打断另外两仓？

**最根本的矛盾**：`BRIDGE_VERSION` 与 `SUPPORTED_CONTRACTS` 是**两套号**
（实测：worldbuilder `1.1.0`、an-engine `1.1.0`、3dworld `1.0.0`）。
若契约号再跟随某一仓，就出现「`1.1.0` 到底是 worldbuilder 的号、还是契约的号」
这种**语义打架**。契约号的唯一职责是回答「**接缝形状**变了没有」，
一旦它开始回答「谁最近发了版」，它就答错问题了。

### 5.3 反向推演：假如**不**做契约版本化

三仓静默漂移：worldbuilder 把 `make_height_sampler` 改名，3dworld 侧
`terrain_mesh` 拿到的采样器形状不对——但 `isinstance` **仍然可能通过**
（只要方法名还在），装配期不报错，**运行期才炸**，而且往往炸在
「地形看起来不对」这种极难定位的地方。

这正是 `_version.py` docstring 的原话：
「若不做版本化，三仓静默漂移，装配期不报错、运行期才炸 —— 这正是整合最容易死的点。」

### 5.4 第三种错误：把契约号和**组合仓自身**的号合一

`../release/版本策略.md` §1 已经把两套号分开了，这里补一条**为什么必须分开**的
补充论据（在 §4.1 那条实测之上）：

- 组合仓号计量「**装配层**变了没有」；
- 契约号计量「**跨仓接缝**变了没有」。

两者**影响面完全不同**：新增一条门禁（装配层变）不影响任何提供方；
给契约加方法（接缝变）会让所有提供方装不上。

更关键的是：实测证明**在 `isinstance` 判定模型下，给 `Protocol` 加方法
是破坏性变更**（老提供方在装配期直接被拒）。若两套号合一，
「新增一条门禁」（向后兼容的 minor）和「给契约加方法」（破坏性的 major）
会撞进同一个号，**无法区分**。

⇒ 两套号必须分开，这是**功能性必需**，不是记账偏好。

## 6. 扩展性分析：这条链上缺什么、什么是有意不做的

> **本节最要紧的一句**：本仓只做「契约、桥接、装配、门禁」。
> 很多事是**有意留给三仓的**，不是缺口。
> **把「有意不做」写成「缺口」会导致无谓的架构膨胀**——
> 那才是真正伤害这个仓库的做法。
>
> 判据：**跨仓接缝 = 数据必须跨越仓边界的地方**。
> 只在一个仓内部发生的事，无论多重要，都不是本仓该管的事。

### 6.1 现状覆盖（实测）

| 环节 | 覆盖情况 |
|---|---|
| 世界生成 → 地形 | ✅ `terrain_source` + `terrain_sink` + `render_sink` |
| 世界生成 → 玩法 | ✅ `worldspec_source` + `mapgraph_source` + `gameplay_world` |
| 玩法 → 表现（**实体**那一格） | ❌ **空**（见 §6.2） |
| 数值规则 | ✅ `rules_kernel` |
| 地牢生成 | ⚠️ 契约齐备，但**无仓内生产消费方**（见 §6.3） |

### 6.2 真缺口（真需要跨仓契约，但今天没有）

**缺口 1：实体 / ECS 接缝——链条上最明显的那一格。**

现有 8 条契约把**地形**接通了，但「玩法产生实体 → 表现层渲染实体」这一格是空的：

- an-engine 有 `core/ecs.py`（类型安全 ECS：自增 id、组件查询、延迟排序）；
- 3dworld 有 `core/entity_core.py` 与 `EntityCore` 契约（`spawn(kind, pos, **kw) -> int`）。

两边都有能力，**但没有一条跨仓契约说「实体的形状是什么」**。
后果不是「现在跑不起来」（现在确实跑得起来），而是
**一旦要做「玩法里生成一个怪物、表现层把它画出来」，就没有可依据的接缝形状**，
只能各自拍脑袋定，然后静默漂移。

**这是本仓最该补的下一个契约**。补它时注意：既有 `entity` 概念在 3dworld 内部
已有契约，**跨仓接缝应当「上提」而不是「另建一套」**（§3.3 的「上提而非新建」纪律）。

**缺口 2：存档与「世界身份」的绑定。**

- an-engine 有 `systems/save_load.py`（多槽位存档、自动存档、版本兼容检查）
  与 `core/world_serial.py`；
- worldbuilder 有 worldspec v1。

**但 worldspec v1 的 `meta.json` 没有内容哈希，也没有 world id**
（实测字段：`spec` / `generator` / `seed` / `size` / `tile_m` / `up_axis` /
`handedness` / `sea_level` / `height_scale_m` / `wind` / `layers` / `rivers` /
`lakes` / `pois` / `graph`）。

⇒ 存档文件**无法声明「我属于哪个世界」**。存档与世界的对应关系，
目前只能靠调用方自己在存档里手写一个目录路径——**没有任何机器保证**。

这条缺口的性质很清楚：**不是「存档功能缺失」，而是「缺一小片跨仓的身份契约」**。
需要的可能只是一个「世界身份」的最小形状（`spec` + `seed` + `size` + `tile_m`
+ 内容摘要），而不是一套存档系统。

**缺口 3：固定步长语义——「用注释对齐语义」的典型复发。**

- an-engine：`core/game_loop.py::FixedTimestepLoop`
- 3dworld：`engine/fixedstep.py::FixedStepper`

**实测：3dworld 的 docstring 明写「实现语义对齐 siwpan/an-engine 的
`allin_engine/core/game_loop.py: FixedTimestepLoop`」**——
也就是说，两个仓各写了一套固定步长实现，靠**注释里的口头约定**保持语义一致。

这恰恰是契约层要消灭的模式：**语义靠注释同步 = 迟早漂移**，而且漂移了不会报错
（跑起来只是「手感不对」，极难归因）。
现在没有跨仓的「时间步 / 时钟」契约，两个仓各自演化时步语义时没有拦截点。

**缺口 4：跨仓事件（半缺口，需要一次决策而不是立刻补契约）。**

- an-engine 有自己的 `core/event_bus.py`（递归保护、安全遍历、容错、装饰器订阅、once）；
- 3dworld 走 cordis 的事件机制。

「玩家死亡 → 播放音效」「开门 → 触发特效」这类**玩法→表现**的通知，
目前没有跨仓契约。但它**未必需要新契约**——cordis 的事件机制**本来就横跨三仓**
（本仓就是 cordis 装配的）。所以这条的结论是
**「先决定 cordis 事件是否充当跨仓事件总线，再决定要不要加契约」**，
而不是直接加一条 `event_source`。这是**一次架构决策**，不是一条契约。

### 6.3 有意不做（**不是缺口，是纪律**）

这一类必须写清楚，否则会被反复「建议补上」。

| 事项 | 为什么不属本仓 | 依据 |
|---|---|---|
| **音频** | 表现层内部事务。3dworld 已有 `engine/audio.py` + `core/audio_core.py`（`AudioCore`），是它自己 15 个内部契约之一。跨仓加音频契约 = **两套契约漂移** | `protocols.py`「上提而非新建」 |
| **资源 / 资产管理** | 3dworld 有 `world3d/asset/`，an-engine 有 `core/data_library.py`，**各仓自管**，当前无跨仓需求 | 本仓职责边界 |
| **网络同步** | 本仓是**本地装配仓**，无联机目标。加了就是凭空扩范围 | README 四条纪律 |
| **实体/ECS 之外的玩法系统** | 战斗、库存、任务、解谜都在 an-engine `systems/` 内部，属该仓内务 | 本仓职责边界 |
| **世界生成算法** | 纯 numpy、无 GL 的实现细节，属 worldbuilder 内务 | 本仓「不含任何算法」 |
| **camera / input 绑定** | 3dworld 的相机「只维护状态，不碰窗口/输入」；an-engine 自带 `systems/input.py`。各管各的 | 各仓内务 |
| **性能 / 资源预算管理** | 本仓是 headless 装配与门禁层，不做运行时资源治理 | 本仓职责边界 |

> **注意 an-engine 与 3dworld 都有音频这件事**：这是**两个仓各自的能力重叠**，
> 但**不构成本仓的缺口**——因为跨仓接缝只在「数据必须跨越仓边界」处才需要。
> 只有当「玩法要触发表现层音效」成为真实需求时，才需要一条接缝；
> 那时更该问的是「cordis 事件够不够」，而不是「再加一条音频契约」。

### 6.4 `dungeon_source` 的诚实说明

`dungeon_source` 契约齐备、版本已登记、桥接已实现、
`tests/test_pipeline.py` 也有形状断言（`test_dungeon_graph_shape_matches_worldspec_contract`）。
但**仓内没有生产消费方**——没有任何代码消费 `dungeon_graph` 的产物。

这是**已铺好但尚未接上的一段管线**，不是缺口（形状已在、门禁已在），
也不是「实现了但没人用」的浪费（它是 §6.2 缺口 1/4 的前置件：
实体与事件接缝一旦落地，地牢图就是玩法世界的天然内容来源）。

**诚实边界**：§3.1.3 实测出的「地牢语义经文件路径会丢」这件事，
当前**没有任何文档或测试记录**。本设计文档补上了认知，但**代码里还没有守卫**。

## 7. 契约与实现分离的**代价**

### 7.1 分离带来的收益

1. **零依赖**。`contracts/protocols.py` 只 `import typing`——
   实测**不 import 任何一仓**。这让契约层可以被任何一侧独立引用，
   而不触发对另两仓的依赖。这是「三仓互不引用」纪律**在契约层自己身上的落实**。

2. **不强制名义子类型**。提供方不必 `class WorldbuilderBridge(WorldSpecSource)`，
   不必继承任何东西。鸭子类型让**同一个契约**可以同时被
   「cordis 的 Service 子类」和「普通对象」满足——
   实测 `selfcheck.py` 里的 `_WorldSpecProvider` 就是一个纯普通类。

3. **同名方法不必同签名即可先跑起来**，配合版本区间，
   给「形状漂移」留出**在装配期被抓住**的一线机会。

4. **版本与结构解耦**。版本号放在 `CONTRACT_VERSIONS` 注册表里，与 Protocol 本体分离
   ——结构校验（`isinstance`）与版本校验互不干扰。

### 7.2 分离带来的风险（全部实测）

**风险 1：签名完全不被检查。**

`isinstance` 对 `runtime_checkable` Protocol **只查方法名存在性**。
实测：把 `generate` 的签名改成完全错误的样子（`generate(self, wrong, args)`），
`isinstance(obj, WorldSpecSource)` **依然返回 True**。

⇒ 契约层保证的是「**方法名在**」，**不是「调用得通**」。
签名/返回形状的保证必须由**别的机制**补：
本仓靠**测试断言真实数据形状**（如 `test_m1_sampler_matches_heightfield` 断言
采样器与阵列逐点一致、`test_dungeon_source_produces_solvable_graph` 断言
`keys`/`entrance`/`boss` 齐全）来兜。

**风险 2：加方法即破坏（已实测）。**

```
isinstance(Impl(), Old) = True      # Old 只有 a
isinstance(Impl(), New) = False     # New 有 a 和 b
```

⇒ 老提供方在**装配期**直接被 `check_provider` 拒掉，即使那个方法对它毫无影响。
这直接决定了新增契约的做法：**必须是新的 `Protocol`，
不能往已有 `Protocol` 里塞方法**（与 `../release/版本策略.md` §3.2 一致）。
历史上的 `dungeon_source` / `rules_kernel` 正是作为**两个新契约**加进来的
（commit `6cfcbea`），而不是往已有契约里塞方法——**这个纪律已经被实践验证过一次**。

**风险 3：`isinstance` 在 cordis 的包装下会失效。**

cordis 会把 `provide` 的值包成 `_InstanceView`，此时对 Protocol 做 `isinstance`
**可能不成立**。`superengine/bridges/terrain_backends.py` 里已经踩过这个坑，
那处的 `satisfies_terrain_sink` 改成了**按方法存在性**判定，并明确注释：
「`isinstance` 对 Protocol 在这种情况下可能不成立，所以这里按方法存在性判定 ——
更稳，也更能给出『缺哪个方法』的明确信息。」

⇒ 代价的直接体现是：**同一个「结构校验」在本仓里有两处实现**
（`check_provider` 用 `isinstance`、`satisfies_terrain_sink` 用方法存在性）。
两处判定逻辑**可能漂移**——这是分离的账，现在记在这里。

**风险 4：返回形状的语义完全不管。**

实测：`dungeon_graph` 产物里的 `keys` / `entrance` / `boss` / `stats`
在 `worldspec.save()` 与 `MapGraph.from_worldspec()` 两道关口上被丢弃，
而**契约校验一声不吭**（§3.1.3）。契约层看不见「语义」，
只能看见「有没有这个方法」。

### 7.3 收益 / 风险对照小结

| 维度 | 分离得到 | 分离付出 |
|---|---|---|
| 依赖 | 契约层零依赖，不 import 三仓 | 签名/语义无机器保证，靠测试兜 |
| 演进 | 契约可独立版本化、跨仓协作 | 加方法 = 破坏性变更（已实测） |
| 校验 | 版本 + 结构双校验在装配期 | 结构判定有两处实现，可能漂移 |
| 表达力 | 提供方无需继承，实现自由 | 鸭子类型判定在 cordis 包装下会失效 |

**结论**：这个取舍是**划算的**，但代价必须被**显式承担**——
承担方式就是 §7.2 那四条对应的守卫：
测试断言真实形状、新契约只增不改、判定逻辑单一化（待办）、语义敏感处补文档。

## 8. 给下一个人的 6 条速记

1. **契约层是底线，不是便利**。三仓互不引用还能协作，全靠这一层。
2. **两条正交轴**：要活对象/同进程 ⇒ 服务契约；要耐久值/跨时间跨机器 ⇒ 文件契约。
   **判据 1**（活对象 vs 耐久值）最关键。
3. **契约版本 ≠ 文件格式版本 ≠ 组合仓版本**。三套号，互不派生。
4. **同形复用的边界比「同形」窄**：复用的是拓扑字段词汇，
   **地牢语义（钥匙/入口/Boss/stats）经文件路径会丢**（实测）。
5. **加方法 = 破坏性变更**（实测）。新能力走**新契约**，永远不要往旧契约里塞方法。
6. **区分「真缺口」与「有意不做」**。真缺口只有 4 个（§6.2）：
   实体接缝、世界身份、时步语义、跨仓事件（需先决策）。
   音频/资源/网络/玩法内部系统都是**有意留给三仓的**。
