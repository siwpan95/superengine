## 0. 口径：这里说的「覆盖」不是行覆盖率

本仓**不使用** `coverage.py`，没有行覆盖 / 分支覆盖百分比。全部是**断言式门禁**：
每个 `test_*` 函数打两行 `ok:`，聚合 runner 按 `ALL_*_TESTS_PASSED` 尾标记判定。
所以「覆盖率」在这里指**「哪一类失效模式有断言挡着」**。

| 覆盖类型 | 含义 | 本仓由谁承担 |
|---|---|---|
| 声明面 | 清单 / 快照 / 文件存在性，不 import 三仓也能跑 | `test_baseline`（9） |
| 结构面 | 版本区间、依赖图、fiber 终态 | `test_assembly`（9） |
| 边界面 | 三仓互不 import、bridges 是唯一进口 | `test_no_cross_import`（3） |
| 行为面 | 端到端数据流、热重载、实现替换、开发循环 | `test_pipeline` / `live` / `backends` / `devloop`（27） |
| 平台面 | Windows / Linux headless / macOS | CI 三 job（**2026-11-05 三平台 runner 全绿**，见 §4） |
| 负向 | 故意给坏输入，确认「被拒而不崩」 | 零散分布在 3 个模块，见 §1 |

计数：**56 个测试函数 / 112 行 `ok:` / 8 模块 / `ALL_TESTS_PASSED`**，与 [回归基线 §0](回归基线.md) 一致。

## 2. 按契约 / 里程碑的覆盖映射

### 2.1 八个契约各自被谁碰过

| 契约 | 结构断言 | 端到端行为 | 仅快照 |
|---|:---:|:---:|:---:|
| `worldspec_source` | ✓ | `test_m1_worldspec_roundtrip` | ✓ |
| `terrain_source` | ✓ | `test_m1_sampler_matches_heightfield` / `test_m1_worldbuilder_to_3dworld_terrain` | ✓ |
| `dungeon_source` | ✓ | `test_dungeon_source_produces_solvable_graph` / `...shape_matches_worldspec_contract` | ✓ |
| `mapgraph_source` | ✓ | `test_m2_provides_mapgraph_into_hosted_context` | ✓ |
| `gameplay_world` | ✓ | `test_m2_anengine_hosts_gameplay_world` | ✓ |
| `rules_kernel` | ✓ | `test_rules_kernel_rolls_dice` | ✓ |
| `terrain_sink` | ✓ | `test_m1_worldbuilder_to_3dworld_terrain` | ✓ |
| **`render_sink`** | ✓ | **✗ 无** | ✓ |

> **G1（唯一一个契约没有端到端测试）**：`render_sink` 的
> `terrain_from_heightfield` 只在 `isinstance` 结构校验和快照里出现，
> 从没被真跑过一条数据。它是「备用路径」，长期不碰就容易与 `terrain_sink` 漂移。
> 建议：补一条最小端到端（给一个 `hm`，断言返回 `dict` 且顶点数 > 0），成本很低。

## 3. 明确未覆盖（缺口登记表）

> **这一节是本文的重点。** 全绿只说明下表以外的失效模式被挡住了。
> 级别沿用 [门禁标准 §0](门禁标准.md)：P1 = 发布前必须解决，P2 = 登记即可带病推进。

| # | 缺口 | 为什么没覆盖 | 风险 | 级别 | 建议 |
|---:|---|---|---|---|---|
| G1 | `render_sink` 无端到端 | 备用路径，优先级低 | 与 `terrain_sink` 静默漂移 | **P2** | 补 1 条最小端到端（§2.1） |
| G2 | ~~Linux / macOS runner 从未实跑~~ **已闭环** | 2026-11-05 Actions run 41915638126 三 job 全 success | — | ✅ 已闭环 | 证据见 §4；后续每次 push 由 CI 自动复验 |
| G3 | 真实 GL / 窗口 / 渲染 | **by design**：本仓全程 headless、零 GL | 表现层真实渲染问题不会在这里暴露 | P2（显式接受） | 归 3dworld 自己的测试域，本文只登记边界 |
| G4 | 跨进程 worldspec 端到端 | `test_m1_worldspec_roundtrip` 是同进程落盘再读 | 独立解释器 / 跨版本读盘的兼容没验 | P2 | 需要一个 `subprocess` 起的读侧，成本中等 |
| G5 | `dungeon_source` 无仓内消费方 | 契约先行，下游未接（主设计 §6.1 标为真缺口） | 契约形状可能「自说自话」 | P2 | 等接入玩法侧时补端到端 |
| G6 | 契约**形状变更 ↔ 三仓区间声明**的「单边」漂移 | `test_baseline` 已用 `EXPECTED_METHODS` 把每个 Protocol 的**方法名集合**锁成快照，单边加 / 删 / 改名方法立刻红；`test_assembly` 验版本在区间内 | 剩余风险：**协同加方法**（Protocol + 提供方同步加、但忘升 `CONTRACT_VERSIONS`）靠装配期 `check_all` 的「版本不在区间」拦截，属版本闸门职责 | **P2**（初判 P1，复核后降级，见 §4） | 形状真空的 Protocol 侧已闭环（2026-11-05 加 `EXPECTED_METHODS`）；协同加方法的残余由版本闸门 + code review 兜底 |
| G7 | 「同形」是约定不是类型保证 | `dungeon_graph` ↔ `graph.json` 靠 1 条字段比对测试 | 任一侧加字段就漂 | P2 | 把字段对照抽成共享常量 / schema，或至少加双向断言 |
| G8 | 性能 / 内存 / 大规模网格 | 无基准 | 大 `grid` / `levels` 下的退化无预警 | P2 | 需要基准脚本，不进 CI 快路径 |
| G9 | 并发 / 多线程热重载 | `dev` 刻意用单线程轮询（0.5s） | 并发改配置 + 改源码的竞态未验 | P2 | 文档已写「轮询是为确定性」，属有意取舍 |
| G10 | 依赖版本上界兼容性 | `PyYAML<7` 等只锁声明，不测实际兼容 | 上界内的小版本可能不兼容 | P2 | 交给 CI 的 `pip install` 实测；不额外做矩阵 |
| G11 | ~~`pyglet` 懒加载仅 Windows 实测~~ **已闭环** | Linux / macOS job 的「依赖面探测」step 均 success | — | ✅ 已闭环 | 三平台 job 均含该 step 且通过 |
| G12 | cordis Loader **吞异常**这一行为本身无专门负向测试 | 靠 `_preimport()` 绕过，不测 Loader 的错 | 若 cordis 升级改了行为，门禁可能失效 | P2 | 加一条「构造期抛异常时 `_preimport` 必须让它浮出来」 |

## 4. 优先级小结

**发布前必须处理（P1）只有一项，跟「平台宣称」有关 —— 该项已于 2026-11-05 闭环：**

- **G2 / G11（✅ 已闭环）**：GitHub Actions run
  [`41915638126`](https://github.com/siwpan95/superengine/actions/runs/41915638126)
  由 SSH 直推触发，`ubuntu-latest` / `macos-latest` / `windows-latest`
  三个 job 全部 `completed / success`，所有 step 通过；
  Linux job 的「依赖面探测（证明本仓不需要 X11/GL）」证据 step 也 success。
  ⇒ 「Windows / Linux headless / macOS 三平台全覆盖」**已兑现**，
  `pyglet.math` 纯 Python 的结论在 Linux / macOS runner 上得到实证。
  ⇒ `v0.1.0` 打 tag 时豁免的「runner 验证闭环」前置**已补验兑现**。

**G6 已从 P1 降为 P2**（full 全评审复核后）：形状真空的 **Protocol 侧已机械闭环** ——
`test_baseline.py::test_protocol_methods_are_declared` 用 `EXPECTED_METHODS` 快照把每个
Protocol 的方法名集合**逐字节锁死**，单边加 / 删 / 改名方法（不改快照）会立刻红
（已用「注入 `new_experimental_method`」变异体实测：断言翻红、RC=1，证明断言有牙）。
升契约版本时装配期 `check_all` 会因「版本不在区间」拒绝，逼着三仓同步区间。
剩余风险**仅一种**：**协同加方法**（Protocol + 提供方同步加、但忘升 `CONTRACT_VERSIONS`）
—— 这类改动两侧一起动，快照与 `test_assembly` 都拦不住，只能靠版本闸门
（`check_all` 的区间校验）+ code review 兜底。两边职责分明，不重复建设。

其余均为 P2，**允许带病推进，但必须显式登记在本文** —— 这正是本文存在的理由。
`G3`「真实 GL 渲染」与 `G9`「并发热重载」是**有意取舍**，不是疏漏，别当成待修 bug。

> 行为面占约 63%，声明面占约 16% —— 这个比例是刻意的：
> 2026-11-04 的 `pyglet` 事故证明，**光有行为面（本机 venv 全绿）挡不住声明面漏项**，
> 所以补了整整一个 `test_baseline` 模块。别再把它当成「冗余的快照测试」删掉。

## 6. 诚实边界与失效条件

- 本审计是**快照**：新增 / 删除测试、新增契约、CI 矩阵调整后必须重跑并回写，
  失效条件同 [回归基线 §6](回归基线.md)。
- 「没有行覆盖率」是事实陈述，不是「不需要行覆盖率」的价值判断；
  若将来引入算法代码（目前本仓**不含任何算法**），这条要重新评估。
- 缺口登记表里的 P1/P2 是**当前判断**，随平台验证结果与发布节奏调整；
  调整时保留调整理由，别只改级别。
