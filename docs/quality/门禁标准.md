# 门禁标准 —— 什么算红、什么算黄

> 时点：2026-11-04 ｜ **状态更新 2026-11-05：三平台 runner 全绿，G2 / G11 已闭环（见 §3）** ｜
> 配套：[回归基线](回归基线.md)、[测试覆盖审计](测试覆盖审计.md)、
> [CI 定义](../../.github/workflows/ci.yml)、[架构总览](../architecture/架构总览.md)。

## 0. 分级口径

| 级别 | 含义 | 处置 |
|---|---|---|
| **P0 阻断** | 干净机装完依赖跑不起来 / 装配没真成 / 三仓互相耦合了 | **不许合并、不许打 tag**。CI 必须红 |
| **P1** | 能力缺失或行为不符，但组合还能跑 | 合并前必须解决；发布前必须解决 |
| **P2** | 文档漂移、覆盖缺口、可读性 | 记录进复盘，允许带病推进，但要显式登记 |

一条硬规则：**判定「装配成功」看输出标记，不只看退出码**。
`boot --report` 必须打出 `SUPERENGINE_BOOT_OK`，`dev --once` 必须打出
`SUPERENGINE_DEV_OK`。退出 0 却没打这行 = 装配没真成（P0）。

## 1. 三道装配门禁（治 cordis 已记录的坑）

| 门禁 | 实现位置 | CI 对应 step | 红了意味着什么 | 历史踩过的坑 |
|---|---|---|---|---|
| entry `name` 白名单 | `assembly.py` 的 `ALLOWED_ENTRY_PREFIXES = ("superengine.bridges.",)` | 装配门禁 | 配置树里出现了不在白名单的 entry | cordis 把 entry `name` 当模块 import ⇒ **配置里一个名字就能执行任意代码** |
| 装配前手工 `import` | `assembly.py` 的 `_preimport()` | 装配门禁 | 某个 bridge 模块构造期抛异常 | cordis Loader **会吞掉插件构造期异常**，只表现为「服务不就绪」，真实异常被藏起来 |
| 终态断言 ACTIVE | `assembly.py` 的 `_assert_all_active()` | 装配门禁 | 有 fiber 停在 PENDING / FAILED | **PENDING 静默**：`inject` 里依赖名拼错，cordis 不报错、只一直等，进程可能静默退出 |

第四道（不算装配门禁，但同属 P0）：

| 门禁 | 实现位置 | CI 对应 step | 红了意味着什么 |
|---|---|---|---|
| 三仓互不引用扫描 | `tests/test_no_cross_import.py` | 全量回归 | 有人图省事跨仓 import，三仓从「可独立发布」退化成「一损俱损」 |

### 排障提示（很重要）

`_locate.py` 的 `import_bridge()` 会把 `ImportError` 包成
`RepoNotFound: 仓 '3dworld' 缺少 bridge 接口模块`。**这句话会误导**——
真实原因常常是**依赖缺失**，藏在末尾的 `原始错误：` 之后。

2026-11-04 实证：缺 `pyglet` 时报「3dworld 缺少 bridge 接口模块」，
**首个失败点**是 `world3d/engine/mathkit.py:19` 的
`from pyglet.math import Mat4, Vec3`；但 `world3d/engine/timeline.py:21` 的
`from pyglet.math import Quaternion, Vec3` 是**并列的第二个顶层入口** —— 两者都挂在
`world3d/engine/__init__.py` 的无条件导入下（`:30` 拉 ①、`:36` 拉 ②），另有
`texproj → geometry → mathkit` 二次抵达 ①。实测「只把 mathkit 改纯 Python」仍会
在 ② 上炸，所以别按「改一处就能摘掉 pyglet」排障。详见
[`../architecture/ADR-004`](../architecture/ADR-004-依赖声明单一事实来源与锁版.md)
与 [`../architecture/已知风险与缓解.md`](../architecture/已知风险与缓解.md) §1。
⇒ **看报错必须看到 `原始错误` 那一段**；`scripts/bootstrap.py` 已经把
「依赖缺失」与「仓没找到」分开探测了。

## 2. CI 的六个闸门（按执行顺序）

三个 job（Windows / Linux / macOS）结构一致，各自依次守：

| # | step | 守什么 | 级别 |
|---|---|---|---|
| 1 | 四仓布局校验 | 三个兄弟仓与 vendored cordis **并排就位**，目录名 ≠ 包名不能改 | P0 |
| 2 | 安装运行时依赖 | `pip install -r requirements.txt`（`-e .` 转发）在干净机能完成 | P0 |
| 3 | 依赖自检 / 依赖面探测 | 清单里的包**真的能 import**；不重复 `pip install` 掩盖漏声明 | P0 |
| 4 | `bootstrap.py --check-only` | **不设 `CORDIS_SRC`**，强制走 vendored cordis 自动回退路径 | P0 |
| 5 | `selfcheck.py` | 契约层无头自检（23 checks）；不依赖 cordis / 三仓，最便宜的前置闸门 | P0 |
| 6 | 装配门禁 + 全量回归 + `dev --once` | 成功标记 / 8 模块（以 `tests/run_tests.py` 的 `MODULES` 表为准）/ 开发循环 | P0 |

**为什么第 4 步刻意不设 `CORDIS_SRC`**：一旦有人把接线改回「必须手工设置环境变量」，
CI 立刻红。这是 3dworld CI 已验证过的门禁思路，本仓沿用。

## 3. 一条需要留痕的跨仓认知纠偏

> `3dworld/.github/workflows/ci.yml`（四仓并排时从父目录起算）注释写：
> 「即使开 headless，X11 那几个库也必须装 —— `import pyglet` 会无条件加载 xlib
> 事件循环（`pyglet/app/__init__.py` 的 else 分支）」

**该判断对 pyglet 的渲染路径成立，对 superengine 的装配路径不成立。**
2026-11-04 本机实测（`sys.modules` 前后差）：

```
测 1  from pyglet.math import Mat4, Vec3
      → ['pyglet', 'pyglet.math']；app/gl: []
测 2  完整装配链路 import world3d.bridge
      → ['pyglet', 'pyglet.math']；重量级模块(会拉 X11/GL): []
测 3  pyglet 2.1.16 顶层 __init__.py：含 app 导入 False / 含 gl 导入 False
      pyglet/math.py 的全部 import：math / typing / warnings
```

pyglet 2.1.16 顶层是**懒加载**，`import pyglet` 本身不碰 app/gl/display/window；
superengine 只走 `pyglet.math`（纯 Python，无 ctypes、无 dlopen）。

⇒ 本仓 Linux / macOS job 采用**精简依赖策略**（不装 X11/GL apt 库），
并保留「依赖面探测」step 打印实际加载的 pyglet 子模块作为证据。

### 精简版在 runner 上红了怎么办（回退路径）

1. 先看「依赖面探测」step 的输出：若 `heavy` 非空，说明假设被推翻。
2. 再看 `import world3d.bridge` 的真实异常，别直接判定「平台不支持」。
3. 确认是缺系统库后，在对应 job 加 3dworld CI 里那套已验证的 apt 清单：
   `libx11-6 libxxf86vm1 libxinerama1 libxi6 libxrandr2 libxrender1 libxext6
   libgl1 libglx-mesa0 libegl1 libgl1-mesa-dri libopenal1 libsndfile1`，
   并设 `LIBGL_ALWAYS_SOFTWARE: '1'`（那套清单是从 pyglet 源码的
   `load_library` 调用里读出来的，不是照抄博客）。
4. **把结论回写本文**，别让下一个人重新踩。

### 2026-11-05 状态更新：精简策略已由 runner 实证

**G2 / G11 已闭环。** GitHub Actions run
[`41915638126`](https://github.com/siwpan95/superengine/actions/runs/41915638126)
（SSH 直推触发）：`ubuntu-latest` / `macos-latest` / `windows-latest` 三个 job 全部
`completed / success`，所有 step 通过；Linux / macOS job 的「依赖面探测」证据 step
也 success，**未触发上面的回退路径**（即没有加任何 X11/GL apt 库）。
⇒ 原先那句「本机是 Windows，Linux / macOS 完整链路只能由 CI 自己证明」的**待验证
表述已过期**：CI 已经证明过了。回退路径保留，是因为它是给「将来 3dworld 改了
pyglet 接线、把重量级模块拉进装配链」这种回归用的，不是说当前还没验。

⚠️ **边界仍然要划清（别顺手删）**：runner 实证的是「**superengine 的完整装配链路**
不需要 X11/GL 系统库」，**不是**「3dworld 的渲染 / 开窗口路径不需要」。
后者本仓 CI 从没跑过、也不该由本仓证明 —— 它归 3dworld 自己的测试域
（见 [测试覆盖审计](测试覆盖审计.md) §3 的 G3：真实 GL / 窗口渲染 by design 不覆盖）。
另：Windows job 全绿也不等于「真窗口用例跑过」，本仓 CI 三个 job 都没开窗口。

## 4. 平台矩阵

| job | runner | 定位 | 额外守什么 |
|---|---|---|---|
| `regression-windows` | `windows-latest` | 主战场 / 发布口径，能开真窗口 | 中文输出编码（`PYTHONIOENCODING=utf-8` 放 workflow 级） |
| `regression-linux` | `ubuntu-latest` | 别人 clone 下来第一件事：无显示器无显卡还能不能跑 | 精简依赖 + 依赖面探测 |
| `regression-macos` | `macos-latest` | 兼容性覆盖 | 精简依赖 + 依赖面探测 |

**编码坑**：Windows runner 控制台默认 cp1252，本仓所有输出是中文，
`python -c "…"` 一行式命令会 `UnicodeEncodeError` 退出 1（3dworld CI 2026-10-29 实测）。
`PYTHONIOENCODING` 放 **workflow 级**而非逐 step，因为「下一个写一行式命令的人不会记得」。

## 5. 发布前的额外门禁

CI 绿 ≠ 可以发版。见 [`../release/发布清单.md`](../release/发布清单.md)：
许可核查（NOTICE 随包）、全量回归绿、干净机复现、两端远端无分叉、
中文路径 git 过滤带 `-c core.quotepath=false`。

## 6. 判定速查

| 现象 | 判定 |
|---|---|
| CI 全绿、本机全绿 | 可合并 |
| 只有 macOS 红，且依赖面探测 `heavy` 为空 | **P1**，按 §3 回退路径处理，别急着判平台不支持 |
| `boot` 退出 0 但无 `SUPERENGINE_BOOT_OK` | **P0 阻断**，装配没真成 |
| `RepoNotFound` 且 `原始错误` 是 `No module named 'pyglet'` | **P0**，依赖声明漏了，不是仓丢了 |
| `test_baseline` 报契约注册表漂移 | **按流程走**：要么是有意加契约/升版本，同步基线并跑 `新增契约流程.md`；要么是误改，回滚 |
| 只有文档漂移 | **P2**，登记进复盘 |
